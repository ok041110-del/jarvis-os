# MVP-0022 Observation

**문서 성격**: 구현 중단 기록(Evidence). Architecture 문서가 아니다.
**대상**: `OUT_OF_SCOPE_MARKERS`의 부정형 오탐
**결과**: **코드를 작성하지 않았다.** 시도했던 수정을 되돌렸다
(`git checkout -- development-hq/mvp/engine.py`). 작업 트리는 클린
상태다.

## 목적

MVP-0021 Observation이 남긴 다음 후보("OUT_OF_SCOPE_MARKERS의 부정형
점검 — `'않는다'` 마커 자체가 매우 광범위해 개별 부정형 등록으로
해결되지 않을 가능성이 있어, 다음에 다룰 때는 재현 결과에 따라 Stop이
필요할 수도 있다")를 실측했다. 그 우려가 실제로 맞았다.

## 실측 결과

`OUT_OF_SCOPE_MARKERS = ("않는다", "제외", "범위 밖", "아니다")`
4개를 전수 재현했다.

### 1) "제외"/"범위 밖" — 부분 문자열 오탐이 재현됨

```python
classify('이 기능은 제외하지 않는다.')      # 실제: out_of_scope (틀림 — "제외되지 않음"=포함됨)
classify('이 기능은 범위 밖이 아니다.')     # 실제: out_of_scope (틀림 — "범위 밖이 아님"=범위 안)
```

기존 `NEGATED_MARKER_EXCEPTIONS`/`_contains_marker`(MVP-0018) 방식으로
`"제외": ("제외하지 않는다",)`, `"범위 밖": ("범위 밖이 아니다",)`를
등록해 코드를 수정했다. **`_contains_marker()` 단위 테스트로는 정확히
동작했다** — `_contains_marker(s, "제외")`는 `False`를 정확히
반환했다.

### 2) 그런데 실제 분류 결과는 바뀌지 않았다 — 마커 간 OR 상호작용

`_analyze_requirement()`의 in_scope/out_of_scope 분류는 4개 마커를
`any()`(OR)로 묶어 판단한다:

```python
in_scope = [s for s in sentences if not any(m in s for m in OUT_OF_SCOPE_MARKERS)]
```

`"이 기능은 제외하지 않는다."`라는 문장은 `"제외"` 마커(수정함)뿐
아니라 `"않는다"` 마커(미수정)에도 **동시에** 걸린다. Korean에서
"~하지 않는다"는 표준 부정 어미이므로, `"제외"`를 부정하는 자연스러운
문장은 거의 항상 `"않는다"`를 포함한다. 마찬가지로 `"범위 밖이
아니다"`는 `"범위 밖"`뿐 아니라 `"아니다"` 마커에도 걸린다.

그 결과, `"제외"`/`"범위 밖"`을 개별적으로 고쳐도 **전체 분류
결과(`classify()`)는 전혀 바뀌지 않는다** — `"않는다"`/`"아니다"`가
같은 문장에서 독립적으로 다시 out_of_scope로 분류하기 때문이다.
직접 실행으로 확인했다:

```
제외 마커만: False (고쳐짐)   | 않는다 마커만: True (안 고쳐짐) | 전체 결과: out_of_scope (안 바뀜)
범위밖 마커만: False (고쳐짐) | 아니다 마커만: True (안 고쳐짐) | 전체 결과: out_of_scope (안 바뀜)
```

### 3) "않는다"/"아니다" 자체는 Scope와 무관한 문장 전체를 오탐한다

```python
classify('이 프로세스는 실패하지 않는다.')   # out_of_scope (Scope와 무관한 임의 부정 서술)
classify('이 시스템은 데이터를 손실하지 않는다.')  # out_of_scope (Scope와 무관)
classify('이것은 버그가 아니다.')            # out_of_scope (Scope와 무관)
classify('이 문제는 심각한 것이 아니다.')     # out_of_scope (Scope와 무관)
```

`"않는다"`는 한국어의 표준 부정 서술어 어미이고, `"아니다"`는
표준 계사 부정형이다. 둘 다 **Scope와 무관한 임의의 부정 문장
전체에서 문법적으로 정확하게 매칭된다** — 특정 복합어 안에 우연히
끼어든 것이 아니라, 마커 자체가 원래 의도(Out of Scope 선언 문장
탐지)보다 훨씬 넓은 대상(모든 부정문)을 잡도록 설계되어 있다.

## 왜 기존 방식(`NEGATED_MARKER_EXCEPTIONS`)으로 해결할 수 없는가

`NEGATED_MARKER_EXCEPTIONS`는 "마커가 **특정하고 유한한** 부정
복합어 안에서만 우연히 걸리는" 경우를 예외 등록하는 방식이다
(MVP-0018~0021의 `"불필요하다"`, `"문제없다"`, `"검토가 필요
없다"` 등 — 전부 하나의 복합어/구를 콕 집어 배제).

`"않는다"`/`"아니다"`는 이 패턴에 맞지 않는다. Scope와 무관한 부정
문장은 무한히 다양하다(`"실패하지 않는다"`, `"손실하지 않는다"`,
`"버그가 아니다"`, ...) — 유한한 예외 목록으로 나열할 수 있는
집합이 아니다. 이를 실제로 고치려면 다음 중 하나가 필요하다:

1. `"않는다"`/`"아니다"`를 Scope 관련 동사(`"포함하다"`, `"다루다"`,
   `"지원하다"` 등)와 결합했을 때만 매칭하도록 마커 판정 로직을
   근본적으로 바꾼다 — 새로운 화이트리스트/규칙 메커니즘이 필요하다.
2. `"않는다"`/`"아니다"`를 `OUT_OF_SCOPE_MARKERS`에서 제거한다 — 이미
   확립된 Capability Logic의 동작(어떤 문장을 Out of Scope로 볼
   것인가에 대한 기존 판단)을 바꾸는 것이며, 그 판단이 지금까지 어떤
   실제 Issue에서 어떻게 작동해 왔는지에 대한 회귀 영향을 판단해야
   한다.

둘 다 "실제로 관찰된 부정 복합어 하나를 예외로 등록"하는 지금까지의
최소 수정 범위를 벗어난다 — Capability Logic의 Out of Scope 판정
방식 자체를 다시 설계하는 결정이다.

## Stop Trigger 발동 결과

**"기존 방식으로 해결할 수 없다"에 해당해 중단했다.** `"제외"`/`"범위
밖"`은 기존 방식으로 등록까지는 가능했지만, `"않는다"`/`"아니다"`와의
OR 상호작용 때문에 그 등록이 실제로는 아무 관찰 가능한 효과를 내지
못한다는 사실을 직접 실행으로 확인한 뒤, 절반만 고치는 것은 "고쳤다"고
말할 수 없다고 판단해 코드 변경 전체를 되돌렸다.
