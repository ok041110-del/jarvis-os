# ADC-0004: Task Dispatcher 승격 재판단 (RFC-0004 후속)

## 목적

RFC-0004가 제기한 질문 중, Development HQ ADC의 권한 범위인 **Task
Dispatcher 승격 여부 하나만** 판단한다. 근거는 `docs/01_mvp/MVP-0001-*`,
`MVP-0002-observation.md`, `MVP-0004-observation.md`,
`docs/governance/observations/OBS-0001.md`,
`docs/governance/observations/OBS-0002.md`,
`docs/02_rfc/RFC-0004-task-dispatcher-runtime-boundary.md`에 실제로
기록된 사실로 한정한다.

## 판단 대상에서 제외

다음은 이 ADC가 다루지 않는다(RFC-0004 §4가 이미 Development HQ ADC의
권한 밖이라고 기록했다).

- Runtime
- Stage Runner
- Pipeline Runner
- Jarvis OS Runtime(Concept Model, ADC-02)

이 ADC는 오직 **Task Dispatcher Boundary**(현재 형태를 유지할지, 승격할지,
보류할지)만 다룬다.

---

## Candidate

Task Dispatcher

## Q1. Hardcoded Workflow가 실제 실패한 사례가 있는가?

**없다.** 지금까지 실행된 세 체인 —
`development-hq/mvp/workflow.py`(MVP-0001),
`workflow_0002.py`(MVP-0002), `workflow_hello_sdlc.py`(MVP-0004) — 는
모두 의도한 대로 동작했다. MVP-0004에서 관찰된 `status: "Failed"` 1건은
디스패치 메커니즘의 실패가 아니라, 입력 Issue에 `description` 키가
없어서 발생한 `KeyError`를 `try/except`가 의도대로 붙잡아 반환한
것이다(`MVP-0004-observation.md`: "실패 경로도 관찰되는가? 예."). 즉
하드코딩된 호출 순서 자체가 깨지거나 잘못 실행된 사례는 관찰되지
않았다.

## Q2. 다음 MVP를 진행할 수 없게 만드는 한계가 관찰되었는가?

**없다.** MVP-0001 → MVP-0002 → MVP-0004로 이어지는 동안, 각 MVP는 새
파일(`workflow_0002.py`, `workflow_hello_sdlc.py`)을 추가하는 방식으로
막힘없이 진행되었다. Implementation Stop Trigger(조건문이 파서/설정
파일로 대체되려는 순간)는 세 MVP 어디에서도 발생하지 않았다
(`MVP-0002-observation.md`, `MVP-0004-observation.md`에 각각 명시).

참고로 MVP-0004 구현 중 실제로 막혔던 지점이 하나 있었으나, 이는 Task
Dispatcher가 아니라 Registry Candidate(`AGENT_CAPABILITY_MAP` 확장이
MVP-0001 테스트를 깨뜨린 사건)였고, 별도 딕셔너리 분리로 해결되었다.
Task Dispatcher 자체가 다음 MVP 진행을 막은 사례는 없다.

## Q3. 현재 문제는 일반화가 필요한 문제인가, 아니면 단순한 코드 중복인가?

**관찰된 사실만 보면, 단순한 형태 반복에 가깝다.** 세 워크플로 파일은
모두 "기존 Agent 함수를 순서대로 호출하고 dict를 반환한다"는 동일한
형태를 반복하지만, 각 파일은 서로 다른 MVP를 위해 독립적으로 작성되었고,
한 파일의 변경이 다른 파일의 변경을 요구한 적이 없다. 세 MVP 어디에서도
"실행 시점에 어떤 체인을 쓸지 동적으로 선택해야 하는" 상황이나 "설정에
따라 호출 순서가 달라져야 하는" 상황은 관찰되지 않았다 — 모든 호출
순서는 작성 시점에 이미 확정되어 있었다. 이는 일반화(동적 배분·조건부
선택)가 필요하다는 근거라기보다, 유사한 모양의 코드가 반복해서 쓰였다는
사실에 가깝다.

## Q4. Keep in MVP를 유지할 수 있는가?

**Q1~Q3의 답변에 근거하면, 그렇다.** 실패 사례가 없고(Q1), 다음 MVP
진행을 막은 사례가 없으며(Q2), 관찰된 반복은 동적 일반화가 필요한
문제라기보다 형태 반복에 가깝다(Q3). 이 세 가지 모두 승격을 정당화할
근거가 되지 못한다.

---

## Decision

**Keep in MVP**

## Decision Rationale

RT-0001의 Task Dispatcher Trigger("하드코딩된 Task 호출 체인 수 ≥ 2")는
OBS-0001·OBS-0002가 확인한 대로 이미 충족되어 이 재평가(RFC-0004)가
열렸다. 그러나 Trigger 충족은 재평가를 시작하는 조건일 뿐, 승격을
자동으로 의미하지 않는다. Q1~Q4에서 실제로 관찰된 사실(실패 사례 없음,
진행 차단 사례 없음, 동적 일반화 필요성 미관찰)은 모두 Keep in MVP를
뒤집을 근거가 되지 못했다.

## Risks

체인 수(3개)와 체인 길이(최대 5단계)는 계속 늘어나고 있으나, 이 결정은
그 성장에 상한을 검증한 적이 없다는 점에 근거하지 않고 "지금까지 실패가
없었다"는 사실에만 근거한다. 다음 MVP에서 체인이 더 길어지거나 여러
체인 중 하나를 실행 시점에 선택해야 하는 상황이 실제로 발생하면, 이
결정은 다시 재평가 대상이 된다.

## Self Review

- Observation만 사용했는가 — **Pass**. Q1~Q4 모두 MVP-0001/0002/0004의
  기존 Observation 문서와 OBS-0001/0002에 실제로 기록된 사실만 인용했다.
- Candidate가 하나뿐인가 — **Pass**. Task Dispatcher만 다뤘다.
- Runtime/Stage Runner/Pipeline Runner/Jarvis OS Runtime을 판단했는가 —
  **아니오**. "판단 대상에서 제외" 절에 명시하고 본문에서 다루지
  않았다.
- 구현을 설명하지 않았는가 — **Pass**. Dispatcher 구현 방법, API,
  자료구조를 제안하지 않았다.
- Architecture Drift가 없는가 — **Pass**. 새 Layer/Component/Service/
  Baseline 없음.
- Kernel Leak가 없는가 — **Pass**. "승격한다/유지한다/보류한다" 외
  구현 암시 표현을 사용하지 않았다.
- RFC-0004와 모순되지 않는가 — **Pass**. RFC-0004가 Development HQ ADC
  권한으로 넘긴 질문(Task Dispatcher 승격 여부)에만 답했고, RFC-0004가
  Jarvis OS 경계로 남겨둔 부분(ADC-02, Runtime 명칭)은 그대로 두었다.
