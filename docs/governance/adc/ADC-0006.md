# ADC-0006: AST Context Module Discovery — Dotted Package Path 지원 확장 여부 (RFC-0008 후속)

## 목적

RFC-0008(Development HQ 수준, `docs/decisions/rfc/
RFC-0008-agents-module-physical-layout-boundary.md`)이 제기한 단일
질문 — "Agent Package Refactoring을 위해 `ast_context.py`의 module
discovery를 평면 module path뿐 아니라 dotted package module path까지
지원하도록 확장하는 것을 허용할 것인가" — 하나만 판단한다.

근거는 RFC-0008 원문, RFC-0008이 인용하는 실제 코드(`hqs/development/
mvp/ast_context.py`, `hqs/development/mvp/agents.py`,
`hqs/development/mvp/tests/test_ast_context.py`,
`hqs/development/mvp/tests/test_stage_01.py`), 그리고
`docs/governance/adc/ADC-0005.md`(RFC-0007 후속, T06~T19 Evidence),
`docs/architecture/core/DEVELOPMENT-HQ-V2.0-FREEZE-0001.md`,
`docs/research/DEV-HQ-V2.0-AGENT-DEFINITION-0001.md`로 한정한다. 이
문서 자체는 새로운 실험을 하지 않는다.

이 ADC는 ADC-0004/ADC-0005와 성격이 같다 — Kernel 승격 여부가 아니라
**Development HQ MVP Implementation 범위 내에서 기존 검증된 정적
분석 함수의 동작 조건을 확장할지 여부**를 묻는다.

## 판단 대상에서 제외

다음은 이 ADC가 다루지 않는다(RFC-0008 Out of Scope와 동일).

- Agent Class/Runtime/Registry/Manager 도입
- 신규 Capability 추가
- Engine 호출 방식, Prompt, Workflow/Stage 로직 변경
- `DEV-HQ-V2.0-AGENT-DEFINITION-0001.md`가 이미 확정한 Agent
  Definition(4개 Agent, 5개 Capability) 자체의 재검토
- `agents.py` → `agents/` 실제 이동(코드 변경) — 이 ADC는 그 이동의
  **선행 조건**만 판단하며, 이동 자체는 이 ADC가 Accept한 이후 별도
  Task다.

---

## Candidate

RFC-0008의 Decision Candidate 3건.

- **A. `agents.py` 유지** — 패키지화를 포기하고 단일 파일 내부만
  책임별로 재정리.
- **B. `ast_context.py`에 dotted package module path 지원 추가** —
  기존 평면 module path 동작은 그대로 두고, 패키지 하위 모듈까지
  발견하도록 additive하게 확장.
- **C. Shim 방식** — 실제 함수는 패키지로 옮기고, `ast_context.py`가
  참조할 대표 함수 1~2개만 담은 별도 평면 파일을 유지.

## Q1. 대안 A로 사용자가 요청한 목표 구조(Agent별 파일 분리)를 달성할 수 있는가?

**아니다.** RFC-0008 §6이 이미 정리한 대로, 대안 A는 `agents.py`를
패키지로 나누지 않으므로 요청받은 `mvp/agents/{requirements,design,
backend,qa}.py` 구조 자체를 만들지 못한다.

## Q2. 대안 C는 Python 제약과 실제로 양립하는가?

**부분적으로만.** `agents.py`와 `agents/`는 같은 디렉터리에 동시에
존재할 수 없다(RFC-0008 §2). Shim이 성립하려면 실제 함수 대부분을
담을 새 패키지와, `ast_context.py`가 계속 참조할 평면 파일 하나를
별도로 유지해야 하는데, 이 경우 패키지로 옮겨진 함수 대부분은 여전히
AST Function Candidate Index/Dependency Closure 밖에 남는다(RFC-0008
§6 표). 즉 대안 C는 목표 구조를 절반만 달성하면서 "평면 파일과 패키지
파일이 같은 책임을 나눠 갖는" 새로운 형태의 복잡도를 추가한다 —
`IMPLEMENTATION_RULES.md`의 "불필요한 추상화 금지" 원칙에 비추어
대안 B보다 우월한 점이 없다.

## Q3. 대안 B는 ADC-0005 Accept 4건의 검증 범위를 그대로 유지하는가?

**유지한다, 단 additive 조건 하에서만.** ADC-0005 판단 1·2가
Accept한 `build_function_candidate_index()`/`build_dependency_
closure()`의 Evidence(T06~T19)는 전부 `hqs/development/mvp/`의
평면 구조 위에서 수집됐다(RFC-0008 §3). 대안 B가 기존 평면 module
path 해석 경로를 **하나도 변경하지 않고** 새 경로(dotted path)만
추가한다면, ADC-0005가 검증한 평면 동작은 코드 경로 자체가 그대로
남아 재작성·무효화되지 않는다. 반대로 기존 로직을 dotted 지원을
이유로 고쳐 쓴다면 ADC-0005 Evidence가 검증한 코드 자체가 바뀌므로
재검증이 필요해진다 — 이것이 이 Decision의 핵심 조건이 되는 이유다.

## Q4. 대안 B는 v2.0 Freeze(`DEVELOPMENT-HQ-V2.0-FREEZE-0001.md`)와 충돌하는가?

**충돌하지 않는다, 조건부로.** v2.0 Freeze §6은 "신규 Architecture/
Component/Concept을 추가했는가 — 아니오"를 Freeze 근거로 명시했다.
대안 B는 새 Layer/Component/Concept을 추가하지 않고, 이미 Freeze에
포함된 `ast_context.py`(ADC-0005 §1/§2) 내부 로직의 동작 조건만
넓힌다. 단, Freeze는 "이미 검증된 v2.0 구현 상태를 Baseline으로
고정하는 것"이므로, 그 구현을 실제로 수정하는 후속 Task는 Freeze
문서가 이미 예정한 대로("Freeze는 결함을 더 이상 수정하지 않는다는
뜻이 아니다") 회귀 검증(109 기준선 유지)을 동반해야 한다.

---

## Decision

**B — Conditional Accept**

## Status

**Conditional Accept**

## Decision Rationale

Q1·Q2가 확인한 대로 대안 A는 목표 구조를 달성하지 못하고, 대안 C는
Python 제약상 패키지 전환의 이점을 온전히 얻지 못하면서 새로운 형태의
복잡도(평면/패키지 이중 구조)만 추가한다. 대안 B가 RFC-0008이 요청한
목표 구조(Agent별 파일 분리)를 그대로 달성하면서, Q3·Q4가 확인한
대로 ADC-0005 Evidence와 v2.0 Freeze 어느 것도 재작성하거나
무효화하지 않는 유일한 대안이다. RFC-0008 §9의 권장 Decision
Candidate를 그대로 채택한다.

Accept를 **무조건**이 아니라 **조건부**로 하는 이유: 대안 B는
`ast_context.py`라는 Frozen/검증된 컴포넌트의 실제 코드 변경을
전제하며, 이 변경의 안전성(기존 평면 동작 무변경)은 선언만으로는
보장되지 않고 구현 후 회귀 테스트로 실증해야 한다. 아래 Conditions는
그 실증 절차를 강제하기 위한 것이다.

## Conditions

구현(별도 Task)이 반드시 지켜야 하는 조건. 하나라도 위반되면 이
Decision은 재검토 대상이다.

1. 기존 평면 module path 동작(`module_source_path("engine")` 등
   dotted가 아닌 기존 호출)은 코드 경로·반환값 어느 것도 변경하지
   않는다.
2. package-aware discovery는 **additive extension**으로만 구현한다 —
   기존 함수의 기존 분기를 고쳐 쓰지 않고, dotted 이름을 처리하는
   새 분기만 추가한다.
3. `ast_context.py` 확장과 `agents.py` → `agents/` 이동은 **별도
   Task**로 분리한다 — 한 Task/커밋에서 동시에 진행하지 않는다.
4. 확장 Task를 먼저 구현하고, `pytest hqs/development/mvp/tests/ -q`
   기준 **109 passed 이상**(회귀 없음)을 확인한 뒤에만 다음 조건으로
   진행한다.
5. `agents.py` 이동은 확장 Task의 (4) 검증이 완료된 이후에만
   진행한다 — 검증 전에 이동을 선행하지 않는다.
6. `agents.py` 이동 시점에 변경이 필요한 테스트 literal(예:
   `test_ast_context.py`/`test_stage_01.py`의 `"agents"` →
   `"agents.backend"` 등, RFC-0008 §5)은 "기존 테스트 Contract
   유지" 원칙의 명시적 예외로, 그 이동 Task 자체에서 사유와 함께
   승인 범위를 기록한다 — 이 ADC가 그 개별 변경 내용을 미리
   확정하지 않는다.
7. ADC-0005가 Accept한 4개 판단(Candidate Index, Dependency Closure,
   Target File Exposure 정책, 기존 구조 유지)의 Evidence 문서(T06~
   T19, `docs/research/DEV-HQ-V2.0-*`)는 재작성하거나 무효화하지
   않는다 — 확장 Task는 새 Evidence를 추가할 뿐, 기존 Evidence의
   결론을 바꾸지 않는다.
8. 기존 평면 모듈(`agents`, `engine`, `project_intelligence`,
   `workflow`, `workflow_project_intelligence` 등) 전체에 대한
   Candidate Index/Dependency Closure 회귀 테스트는 확장 이후에도
   그대로 유지·통과해야 한다.

## Implementation Boundary

이 ADC가 허용하는 코드 변경 범위는 **`ast_context.py`의 module
discovery 로직을 dotted package path까지 인식하도록 넓히는 것
하나뿐**이다. 다음은 이 ADC로 승인되지 않는다.

- Agent class, Agent Runtime, Agent Registry, Agent Manager
- 신규 Capability
- 새로운 orchestration layer
- Engine 호출 방식/Prompt 변경
- Stage 01~05 코드 변경(Stage는 `ast_context.py`의 확장된 함수를
  기존과 동일한 시그니처로 계속 호출할 뿐, Stage 자체의 로직은
  손대지 않는다)
- Workflow Contract 변경
- `agents.py` → `agents/` 실제 이동 — Conditions 3·5에 따라 별도
  Task로만 진행

## Architecture Impact

**NONE** — 대안 B는 Runtime/Registry/Event Bus/Engine Gateway 등
`IMPLEMENTATION_RULES.md` 금지 목록에 해당하는 개념을 추가하지 않는다.
확장 대상은 이미 Kernel 범위 밖(MVP Implementation, `BASELINE.md`
Not Included)으로 확정된 순수 정적 분석 함수 내부 로직뿐이다. 이는
ADC-0005 판단 4("기존 구조 유지 확인")가 사용한 것과 동일한 근거
구조이며, v2.0 Freeze §6의 Architecture/Governance Review 결과와도
일치한다.

## Contract Impact

- `ast_context.py`의 공개 함수 시그니처(`module_source_path(module:
  str) -> Path`, `build_dependency_closure(module: str, function:
  str) -> str`, `build_function_candidate_index() -> str`)는
  변경되지 않는다 — 확장은 각 함수 내부의 모듈 이름→경로 변환 로직에
  한정된다.
- `agents.py`의 함수 시그니처, `AGENT_CAPABILITY_MAP`/
  `HELLO_SDLC_CAPABILITY_MAP` 값, Engine 호출 방식, Prompt 문자열 —
  이 ADC가 승인하는 범위(확장 Task) 안에서는 전혀 변경되지 않는다.
- 테스트 Contract는 확장 Task 자체에서는 영향받지 않는다(Q3, RFC-0008
  §5) — Contract 변경은 후속 `agents.py` 이동 Task에서만, Conditions
  6이 정한 승인 범위 내로 한정해 발생한다.

## Validation

구현(확장 Task) 완료 후 반드시 확인해야 하는 항목.

- `python3 -m pytest hqs/development/mvp/tests/ -q` — **109 passed
  이상, 기존 대비 회귀 없음**.
- `test_ast_context.py`의 기존 5개 평면 module 테스트(Candidate
  Index 3건 + Closure 관련 2건 이상)가 **수정 없이** 통과하는지 확인.
- `test_stage_01.py`의 5개 테스트가 **수정 없이** 통과하는지 확인
  (특히 `test_target_given_computes_dependency_closure`).
- 신규로 추가하는 dotted path 테스트(확장 Task 자체 검증용)는 기존
  평면 module 테스트와 별도 파일 또는 별도 함수로 추가해, 기존 테스트
  literal을 건드리지 않았음을 diff로 확인.
- 필요하다고 판단되면 real Engine E2E 1건(Stage 01 또는 Stage 04
  경로) 재실행 — 단, 확장이 순수 정적 분석(Engine 미호출) 범위라면
  생략 가능(ADC-0005 판단 1·2와 동일한 판단 기준).
- `git diff`로 `ast_context.py` 변경분이 기존 분기를 고쳐 쓴 것이
  아니라 새 분기 추가(additive)임을 확인.

## Follow-up

1. **AST Context 확장** — `ast_context.py`에 dotted package path
   지원을 additive하게 추가(Conditions 1·2).
2. **Regression** — 확장 직후 `pytest hqs/development/mvp/tests/ -q`
   109 passed 이상 확인, 신규 dotted path 테스트 추가(Conditions 4,
   Validation).
3. **`agents.py` → `agents/` 이동** — (2)의 검증이 완료된 이후에만
   착수(Conditions 3·5). 이동 시점에 필요한 테스트 literal 변경을
   해당 Task에서 명시적으로 승인·기록(Conditions 6).
4. 이 순서를 역전하거나 병합하는 구현(예: 확장과 이동을 한 커밋으로
   처리)은 이 ADC의 Conditions 위반이며, 별도 재검토 없이 진행할 수
   없다.
