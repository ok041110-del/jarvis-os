# ADC-0008: Outcome-Oriented Governance Model 도입 여부 판단 (RFC-0010 후속)

## 목적

RFC-0010(Development HQ 수준, `docs/decisions/rfc/
RFC-0010-outcome-oriented-governance-model.md`)이 제기한 Q-1/Q-2/Q-3
Boundary Question을 판단한다.

근거는 RFC-0010 원문과 그것이 인용하는 `docs/governance/README.md`,
`docs/decisions/rfc/README.md`, 그리고 이 ADC가 추가로 확인한
`hqs/development/IMPLEMENTATION_RULES.md`(Stage Data Contract §
Public/Hidden 구분), `docs/architecture/core/
DEVELOPMENT-HQ-V2.0-FREEZE-0001.md`(§4/§7), `docs/architecture/core/
ADR-0018-langgraph-adoption-final-review.md`(Deferred/Not Adopted
선례)로 한정한다. 이 문서 자체는 새로운 조사를 하지 않는다.

이 ADC는 ADC-0007과 같은 성격이다 — Kernel 승격 여부가 아니라
**Governance 절차 자체에 대한 서술을 저장소 문서에 반영할지 여부**를
묻는다. "Accept / Reject / Scoped Accept / Defer" 중 하나로 판단한다.

## 판단 대상에서 제외

- `docs/governance/README.md` 등 실제 Governance 문서의 본문 수정 —
  이 ADC는 채택 여부와 Scope만 판단하며, 실제 문서 반영은 후속 ADR
  대상이다(RFC-0010 §6, 사용자 지시 5번).
- 이미 Resolved된 RFC(RFC-0005/RFC-0007~0012 등)와 기존 Freeze
  문서(`DEVELOPMENT-HQ-V2.0-FREEZE-0001.md` 등)의 결론을 소급
  변경하는 것 — 이 ADC가 필요하다고 판단하는 경우에도 "후속 재평가
  대상"으로만 남기고, 이 판단 자체가 재평가를 수행하지 않는다.
- 사용자 제공 "Jarvis OS Governance v2 Design Principles" 원문의
  P0~P17 전체를 문구 단위로 채택/기각하는 것 — RFC-0010이 좁힌 Q-1/
  Q-2/Q-3 범위로 한정한다.

---

## 판단 1 (Q-1). "Governance v2" 명칭 충돌을 어떻게 해소할 것인가

### Evidence

- 기존 "Governance v2"(Observation 계층: OBS 문서 누적, Rule A/B)는
  `docs/governance/README.md`에 이미 기록되어 있고 RFC-0004/ADC-0004,
  OBS-0001~0006에서 실제로 인용된 확정 명칭이다.
- 사용자 제공 문서는 완전히 다른 내용(Goal-over-Process, Tier 0~4,
  Freeze/Deferred 정책 등)을 같은 제목 "Governance v2"로 지칭한다
  (RFC-0010 §1).
- `docs/decisions/rfc/README.md`는 서로 다른 문서 트리에서 RFC 번호가
  재사용되는 것을 "번호만으로는 구분되지 않는다"는 기존 위험으로 이미
  기록한 바 있다 — 이번 이름 충돌도 같은 유형이다.

### Constraint / Boundary

- CLAUDE.md Frozen Architecture 규칙상 Governance 자체 변경은 RFC →
  ADC → ADR 없이 직접 반영할 수 없다 — 이 ADC가 명칭을 "확정"하더라도
  실제 `docs/governance/README.md` 수정은 이 ADC의 범위 밖이다(후속
  ADR 대상).
- 기존 "Governance v2"(Observation 계층) 명칭과 그 내용(Rule A/B)은
  이 ADC가 재정의하거나 폐기하지 않는다 — RFC-0010이 이미 그 경계를
  명시했다.

### Options

- (a) 같은 이름 유지 — 참조할 때마다 범위를 병기해야 하는 부담이
  계속 남는다.
- (b) 별도 명칭 사용 — 기존 "Governance v2"(Observation 계층)는
  그대로 두고, 사용자 제공 문서는 RFC-0010 제목과 동일한
  "Outcome-Oriented Governance Model"로 부른다.
- (c) 두 문서를 하나로 통합하고 번호를 다시 매긴다 — 통합 범위·방식
  자체가 별도 검토 대상이 되어 이 ADC의 범위를 벗어난다.

### Recommendation

(b). 통합(c)은 이 ADC가 판단하기에는 파급 범위가 크고(Observation
계층의 실사용 이력을 재구성해야 함), 같은 이름 유지(a)는 이름 충돌
문제 자체를 해소하지 못한다. 별도 명칭은 기존 Baseline을 건드리지
않고 충돌만 제거하는 최소 변경이다.

### Final Judgment

**Accept (b).** 사용자 제공 Governance 철학 문서는 저장소에 반영될
경우 "Outcome-Oriented Governance Model"로 지칭한다. "Governance v2"
명칭은 기존 Observation 계층(`docs/governance/README.md`)의 전용
명칭으로 유지하며, 이 ADC는 그 내용을 변경하지 않는다. 실제 명칭
반영(문서 제목·참조 갱신)은 후속 ADR에서 수행한다.

## 판단 2 (Q-2). RFC/ADC/ADR "역할" 재정의(P7~P9, RFC mandatory gateway 포함)를 채택할 것인가

### Evidence

- `docs/decisions/rfc/README.md`는 이미 "RFC는 결정이 아니라 검토
  대상이다. RFC 자체는 Baseline을 변경하지 않는다"고 서술한다 — 사용자
  문서 P7("RFC/ADC/ADR은 미래를 통제하지 않고 현재 시점의 Decision과
  근거를 기록한다")과 사실상 같은 취지다.
- `hqs/development/IMPLEMENTATION_RULES.md`("Stage Data Contract"
  절)는 이미 "Public 변경 시 예외 없이 RFC → ADC → ADR 필요"로
  범위를 좁혀 규정하고 있다 — Hidden/Local 변경에는 RFC를 요구하지
  않는다. 이는 사용자 문서 P8("RFC is a Design Mechanism, Not a
  Mandatory Gateway" — 일반 구현/Refactoring/Bug Fix는 RFC 없이
  진행 가능, Architecture Boundary·Public Contract 변경만 RFC 대상)과
  실무상 이미 일치한다.
- ADC-0007(§ "판단 2")과 RFC-0009 자체가 "Decision + Evidence +
  재평가 조건"을 병기하는 서술 방식을 이미 쓰고 있다 — P9("ADC는
  Constraint/Boundary 기록")와 겹친다.

### Constraint / Boundary

- 이 판단은 **서술을 추가할지 여부**만 다룬다 — 기존에 이미 RFC가
  필요하다고 확정된 대상(Kernel Public Contract, Stage Data Contract
  Public 표 등)의 RFC 요구 여부를 바꾸지 않는다.
- P7~P9 전체를 그대로 옮겨 적으면 기존 `docs/governance/README.md`·
  `docs/decisions/rfc/README.md`의 기존 서술과 중복되거나 표현이
  달라 향후 어느 쪽이 우선하는지 다시 모호해질 위험이 있다.

### Options

- (a) P7~P9 원문을 그대로 새 절로 추가한다.
- (b) 기존 서술과 실질적으로 일치하는 부분만 "참조/명문화 확인"
  수준으로 반영하고, 원문 전체를 옮겨 적지 않는다.
- (c) 채택하지 않는다 — 기존 서술로 이미 충분하다고 본다.

### Recommendation

(b). Evidence가 보여주는 것은 "기존 실무가 이미 P7~P9와 방향이
같다"는 사실이지, "기존 서술이 불충분해서 전면 교체가 필요하다"는
사실이 아니다. 전면 교체(a)는 과잉이고, 완전 불채택(c)은 사용자가
제기한 명확화 필요성 자체를 무시한다.

### Final Judgment

**Scoped Accept.** P7~P9는 기존 관행의 명문화로 판단하며, 반영 시
`docs/governance/README.md` "핵심 원칙" 절에 짧은 참조 문구를
추가하는 수준으로 한정한다 — RFC/ADC/ADR 각 문서의 기존 정의(`docs/
decisions/rfc/README.md`, `docs/decisions/adc/README.md`)를 교체하지
않는다. 기존에 이미 RFC 대상으로 확정된 Public Contract 목록(Kernel
Public Contract, Stage Data Contract Public 표 등)은 이 판단으로
넓히거나 좁히지 않는다. 실제 문구 반영은 후속 ADR에서 수행한다.

## 판단 3 (Q-3). Freeze/Deferred/Tier 정책(P10, P15, P16)을 채택할 것인가, 기존 문서에 소급 적용할 것인가

### Evidence

- `DEVELOPMENT-HQ-V2.0-FREEZE-0001.md` §7은 "Freeze 이후 Architecture/
  Contract 변경은 기존 RFC → ADC → ADR Governance 절차를 통해서만
  진행한다"고 명시하며, Freeze 자체는 "이미 검증된 v2.0 구현 상태를
  Baseline으로 고정하는 것"이라고 규정한다 — 이는 사용자 문서
  P15("Freeze는 실제 Invariant에만")보다는 넓게, "검증된 안정 상태"
  전반에 Freeze를 적용해 온 기존 관행과 정면으로 같지 않다.
- `ADR-0018`은 "선행 Decision(`ADC-0032`/`ADC-0033`의 Not Accept·
  Defer 판정)을 다시 논의하지 않는다"고 명시하며, Deferred 상태를
  향후 재평가 가능하지만 지금 당장 재오픈하지 않는 상태로 취급한
  선례다 — 사용자 문서 P16("Deferred ≠ 영구 금지, 그러나 재평가는
  새 Evidence가 있을 때")과 실질적으로 같은 결과에 도달해 있다.
- `docs/decisions/rfc/README.md`에는 이미 여러 건의 "Not Accepted"
  RFC(RFC-0008~0012, Kernel 트리)가 Resolved 상태로 안정적으로
  남아 있다 — 이 판단이 그 상태를 흔들면 파급 범위가 저장소 전체로
  확대된다.

### Constraint / Boundary

- 사용자 지시 4번: 기존 Architecture/Contract를 임의로 변경하거나
  기존 ADC/ADR의 결론을 소급 변경하지 않는다.
- 이 ADC는 어떤 기존 Freeze 문서나 "Not Accepted" RFC도 재평가
  대상으로 지정할 권한이 없다 — 재평가 여부는 각 문서가 속한
  Governance 절차(RT Trigger, OBS 누적 등)를 통해서만 열린다.

### Options

- (a) Tier 구분과 "Freeze는 실제 Invariant에만", "Deferred ≠ 영구
  금지" 원칙을 **향후 신규 판단에 적용할 참고 원칙**으로만 채택하고,
  기존 Freeze 문서·기존 Resolved RFC에는 소급 적용하지 않는다.
- (b) 위 원칙을 채택하는 동시에 기존 Freeze 문서·"Not Accepted"
  RFC 전체를 즉시 재평가 대상으로 지정한다.
- (c) 채택하지 않는다.

### Recommendation

(a). (b)는 사용자 지시 4번이 명시적으로 금지하는 소급 변경에
해당한다. (c)는 향후 신규 Freeze/Deferred 판단에 Tier 구분이 주는
명확화 가치를 포기한다.

### Final Judgment

**Scoped Accept, 소급 미적용.** Tier 0~4 강도 구분과 "Freeze는 실제
Invariant에만", "Deferred/Rejected ≠ 영구 금지" 원칙은 **이후 새로
작성되는 Freeze/RFC/ADC 판단에만** 참고 원칙으로 적용 가능하다고
판단한다. 다음은 이 ADC로 재평가되지 않으며, 각각 "후속 재평가
대상"으로만 남긴다(재평가 자체를 지금 트리거하지 않음):

- `DEVELOPMENT-HQ-V1.0-FREEZE-0001.md`,
  `DEVELOPMENT-HQ-V2.0-FREEZE-0001.md` 등 기존 Freeze 선언
- `docs/architecture/core/` 트리의 "Not Accepted" RFC(RFC-0008~
  0012)와 `docs/decisions/rfc/`의 RFC-0005(Open, 미해결)
- `ADR-0018`이 이미 종결한 LangGraph Deferred/Not Adopted 판정

이 문서들에 새 Evidence가 발생해 재평가가 필요하다고 판단되면, 그
재평가는 이 ADC가 아니라 해당 문서가 속한 절차(RT Trigger 충족, OBS
누적, 또는 개별 RFC 재개설)를 통해 별도로 진행한다.

## 종합 Decision

**Scoped Accept (Q-1 Accept (b) / Q-2 Scoped Accept / Q-3 Scoped
Accept, 소급 미적용).**

| 대상 | Governance 변경 필요 | 처리 |
|---|---|---|
| Q-1 명칭 분리("Outcome-Oriented Governance Model") | 필요 | 후속 ADR에서 명칭·참조 반영 |
| Q-2 RFC/ADC/ADR 역할 참조 추가 | 필요(제한적 — 참조 문구만) | 후속 ADR에서 `docs/governance/README.md` "핵심 원칙" 절에 반영 |
| Q-3 Tier/Freeze/Deferred 원칙의 향후 적용 | 필요(신규 판단 한정) | 후속 ADR에서 원칙 자체만 명문화, 적용 방식은 각 신규 판단이 개별 결정 |
| 기존 Freeze 문서·기존 Not Accepted/Resolved RFC의 소급 재평가 | 불필요(지금 변경하지 않음) | 재평가 필요 시 각 문서 단위 별도 RFC/RT 절차로 이월 — 목록은 판단 3 참고 |
| `docs/governance/README.md` 등 실제 본문 수정 | (ADC 확정 이후) | 이 ADC는 수행하지 않음 — 후속 ADR이 유일한 반영 경로 |

Baseline 반영 정확한 절 번호·배치, ADR 채번은 후속 ADR 단계에서
확정한다(이 ADC가 결정하지 않음). RFC-0010의 Status/Decision 절은 이
ADC의 결과를 반영해 Resolved로 갱신하고, `docs/decisions/rfc/
README.md` 등록 표의 후속 ADC 칸에 이 문서를 연결한다.

**후속 ADR**: `docs/decisions/adr/
ADR-0010-outcome-oriented-governance-model-baseline.md`. Status는
Proposed(사용자 승인 대기)이며, 승인 전까지 `docs/governance/
README.md`는 이 ADC·해당 ADR 어느 것으로도 수정되지 않는다.
