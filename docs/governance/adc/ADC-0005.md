# ADC-0005: AST 기반 Context 자동 추출 Production 통합 판단 (RFC-0007 후속)

## 목적

RFC-0007(Development HQ 수준, `docs/decisions/rfc/
RFC-0007-ast-context-build-integration.md`)의 재평가 결과 —
**A. INTEGRATION JUSTIFIED(조건부 범위로 한정)**,
`docs/research/DEV-HQ-V2.0-RFC-0007-REVALIDATION-0001.md` — 가
제시한 결정 후보 4건을 개별적으로 판단한다.

근거는 RFC-0007 원문, RFC-0007 Revalidation 문서, 그리고 그 두
문서가 인용하는 T06~T19 Research/Evidence 문서(
`DEV-HQ-V2.0-DESIGN-AST-STARTPOINT-IDENTIFICATION-0001.md`,
`DEV-HQ-V2.0-AST-CANDIDATE-INDEX-REPRODUCTION-0001.md`,
`DEV-HQ-V2.0-TARGET-FILE-EXPOSURE-MITIGATION-0001.md`,
`DEV-HQ-V2.0-CONTEXT-EXPOSURE-REPRODUCTION-0001.md` 등)로 한정한다.
이 문서 자체는 새로운 실험을 하지 않는다.

이 ADC는 ADC-0003과 성격이 같다 — Kernel 승격 여부가 아니라
**Development HQ MVP Implementation 범위 내에서의 채택 여부**를
묻는다. 4개 항목 모두 "Accept / Reject / Defer / Out of Authority
(Escalate)" 중 하나로 판단한다.

## 판단 대상에서 제외

- 실제 구현(함수 작성, workflow 파일 수정) — 이 ADC는 채택 여부만
  판단하며, 구현은 이 ADC가 Accept한 이후 별도 Task다.
- Context 생성 책임의 위치(`project_intelligence.py` 확장 vs 신규
  모듈) — RFC-0007 §4, Revalidation §6이 이미 "이번 재검토 대상
  아님, ADC로 이관"이라고 명시했다. 이 ADC가 그 이관을 받되, 아래
  판단 2에서 최소한으로만 다룬다.
- Workflow/Agent/Model 재설계, LangGraph/State/Prompt Cache, Stage
  06, 다른 HQ 기능 변경 — 이번 재검토(RFC-0007, Revalidation) 어디
  에서도 다뤄지지 않았다.

## 판단 1. AST Function Candidate Index 도입 여부

### RFC-0007 Boundary Summary

시작점(target module/function) 자동 식별을 위해, 저장소 함수
후보를 이름 + signature + docstring 첫 줄만 담은 저비용 Index로
제공한다(본문 없음).

### Evidence

- `DEV-HQ-V2.0-DESIGN-AST-STARTPOINT-IDENTIFICATION-0001.md`(T17):
  Design 원문만(A)/파일 목록만(B)은 식별 실패, AST 함수 후보
  인덱스(C)는 1건 정확히 식별.
- `DEV-HQ-V2.0-AST-CANDIDATE-INDEX-REPRODUCTION-0001.md`: 서로 다른
  성격의 Task 2건 추가 재현, T17 포함 **3/3(100%)** 식별 성공.
  3건 모두 AST 폐쇄 → Build → pytest까지 실제로 통과(전부 real
  Engine).
- 알고리즘은 `ast.parse` 기반 순수 정적 분석이며 Engine 호출을
  포함하지 않는다(RFC-0007 §5) — 실패 모드는 예외뿐이고, 기존
  `try/except` 경로로 흡수된다.

### Decision

**Accept**

### Decision Rationale

3건의 서로 다른 실제 Task에서 실패 없이 재현됐고, 표준 라이브러리
(`ast`)만 사용하는 순수 함수라 새 의존성이 없다. `project_intelligence.py`
가 이미 "파일 목록을 반환하는 순수 함수" 패턴을 갖고 있으므로, 같은
성격의 함수 하나를 추가하는 것은 새 Capability/Agent/Runtime/
Registry를 만들지 않는다(`IMPLEMENTATION_RULES.md` 금지 목록과
충돌 없음).

### Risks

3건 모두 이 저장소(`hqs/development/mvp/`) 규모에서 검증됐다 —
`AST-CANDIDATE-INDEX-REPRODUCTION-0001.md` §다음 Task가 이미 지적한
대로, 함수 수가 수십~수백 개로 늘어난 저장소에서 인덱스 크기·식별
정확도가 유지되는지는 검증되지 않았다. 저장소 규모가 커지면 재검증이
필요하다.

### Next Step

No ADR Required — `hqs/development/BASELINE.md`는 MVP Implementation을
Baseline 범위에서 명시적으로 제외한다("Not Included: MVP
Implementation"). 이 판단은 Baseline 문서 어떤 문구도 변경을
요구하지 않는다.

## 판단 2. AST Dependency Closure 기반 Context 생성 도입 여부

### RFC-0007 Boundary Summary

판단 1에서 식별된 시작점(target module/function)에서 출발해, 직접·
간접 의존성을 추적한 AST 폐쇄만 Build Context에 포함한다(Full
Source 대체).

### Evidence

- T09~T12: 단일/다중 모듈(최대 6~7개), 얕은 호출 그래프에서 Full
  Source와 동등한 Build 정확성.
- T17~T19: 판단 1에서 식별된 시작점으로 실제 AST 폐쇄를 계산해
  Build+pytest까지 3회(T17 1건 + Reproduction 2건) 전부 통과.
  폐쇄 크기: 334자(1개 모듈) ~ 7,643자(5개 모듈) — Full Source
  대비 40~60% 수준(RFC-0007 §6 재인용).
- 기존 코드 손상: T12~T19 전체, 20개 이상의 개별 조건/trial에서
  단 한 번도 발생하지 않았다(RFC-0007 §1, Revalidation §2 재확인).
- 알고리즘은 T11~T19에서 반복 재사용된 약 90줄 내외의 순수 함수
  (`ast.parse` + Load-context 이름 추적 + 상대 import 재귀,
  RFC-0007 §6).

### Decision

**Accept**

### Decision Rationale

정확성(Full Source와 동등)과 안전성(내용 손상 0건)이 4개 이상의
독립 Task, 20개 이상의 조건에서 반복 확인됐다. Project Intelligence
가 이미 확립한 "Context를 문자열로 렌더링해 concatenate"하는 기존
패턴(RFC-0007 §2, §7)을 그대로 재사용하므로 새로운 전달
메커니즘을 만들지 않는다. Build Capability의 함수 시그니처
(`backend_agent_code_generation(design: str) -> str`)도 변경되지
않는다(RFC-0007 §3).

### Risks

Context 생성 책임의 위치(`project_intelligence.py` 확장 vs 신규
모듈)는 이 판단이 결정하지 않는다 — RFC-0007 §4, Revalidation §6이
이미 미해결로 남긴 항목이며, 이 ADC도 그 유보를 그대로 유지한다.
어느 쪽을 택하든 "Project Intelligence는 경로만 반환한다"는 기존
관례와의 정합성은 실제 구현 시점에 다시 확인해야 한다.

### Next Step

No ADR Required — 판단 1과 동일 근거(MVP Implementation은 Baseline
범위 밖).

## 판단 3. Target File Exposure 정책 채택 여부

### RFC-0007 Boundary Summary

기존 파일을 수정하는 Build Task에서 대상 파일 노출이 불가피할 때,
Target Function을 명시하고 그 외 영역의 변경을 금지하는 최소 정책을
Build 프롬프트에 포함한다. 초기 적용은 "기존 함수 1개 확장" 성격의
Task로 제한한다.

### Evidence

- `DEV-HQ-V2.0-TARGET-FILE-EXPOSURE-MITIGATION-0001.md`: 미노출(A)
  조건에서는 "기존 함수 확장"이라는 요구사항 자체를 구조적으로
  충족할 수 없었다(새 함수를 별도로 만드는 것 외 선택지 없음) — 즉
  실제 수정 Task에서 노출은 선택이 아니라 전제조건.
- 노출 + "대상 함수 명시 + 다른 부분 불변 명시" 정책(B, C) 조건에서
  는 반환된 전체 파일의 실제 diff가 **2/2 전부** 지정된 함수 내부의
  순수 추가로 한정됐다(다른 함수/import/공백 변경 없음, pytest 14
  passed).
- T12~T16 누적: 노출 시 재작성 발생률 ~40%였으나, 내용 손상은 16개
  이상 조건 전체에서 0건 — 재작성이 일어나도 항상 정확히 보존됨
  (RFC-0007 §1, Revalidation §2).

### Decision

**Accept**

### Decision Rationale

실제 파일 수정 Task에서 노출이 불가피하다는 것 자체가 구조적으로
증명됐고(A 조건), "대상 함수 명시 + 불변 부분 명시"라는 최소 정책이
노출 상태에서도 Scope 준수를 만들어낸다는 것이 2/2로 확인됐다. 이
정책은 Build 호출 프롬프트에 지시문을 추가하는 것뿐이며, 새
Capability/Runtime/후처리 로직을 요구하지 않는다.

### Risks

Evidence가 **1개 Task, 2개 조건**뿐이다 — Revalidation 문서가 이미
지적한 대로 일반화에 한계가 크다. 이 Accept는 "정책이 항상
충분하다"를 의미하지 않는다. 그래서 이 판단은 RFC-0007 §8-5/
Revalidation §7이 권고한 대로 **초기 적용 범위를 "기존 함수 1개
확장"류의 좁은 Task로 제한**하는 것을 정책의 일부로 함께 채택한다
— 다중 함수 동시 수정, 파일 구조 변경 등 더 넓은 범위는 별도
재검증 전까지 적용하지 않는다. "노출 + 무지시" 조건과의 직접
비교도 아직 없다(Open Issue, 새로 실험하지 않음).

### Next Step

No ADR Required — Build 프롬프트 지시문 추가는 MVP Implementation
범위이며 Baseline 문서를 변경하지 않는다.

## 판단 4. 기존 구조 유지(Workflow/Agent/Model 변경 없음) 확인

### RFC-0007 Boundary Summary

판단 1~3을 채택하더라도 Workflow/Agent/Model의 Freeze 상태를
변경하지 않고, 기존 Context 전달 구조(Project Intelligence가 이미
확립한 "문자열 concatenate" 패턴)만 확장한다.

### Evidence

- RFC-0007 §7: "Runtime, Registry, Event Bus 등 금지된 개념을
  전혀 필요로 하지 않는다(`IMPLEMENTATION_RULES.md` 금지 목록과
  충돌 없음)."
- RFC-0007 §Architecture Impact, Revalidation §4: "없음(NONE)" —
  이번 재검토 전체에서 판정이 바뀌지 않았다.
- 최소 변경 범위(RFC-0007 §8, Revalidation §8)는 기존 workflow
  파일 안에서 Build 호출 직전 한 줄 추가뿐이다 — Workflow의
  하드코딩된 순차 호출 패턴 자체는 그대로 유지된다.

### Decision

**Accept**

### Decision Rationale

판단 1~3 어느 것도 새 Layer/Component/Service, 새 Capability/
Agent, Runtime/Registry/Event Bus 개념을 요구하지 않는다는 것이
RFC-0007 원문과 Revalidation 양쪽에서 반복 확인됐다. 이는 새로운
판단이 아니라, 판단 1~3의 Accept가 실제로 Architecture Drift 없이
성립함을 재확인하는 절차다.

### Risks

없음 — 이 판단이 뒤집히려면 판단 1~3 중 하나가 Architecture 수준
개념을 요구하는 것으로 밝혀져야 하는데, 그런 사실은 관찰되지 않았다.

### Next Step

No ADR Required.

## 미확정 사항 (이 ADC가 결정하지 않음)

- Context 생성 책임의 위치(`project_intelligence.py` 확장 vs 신규
  모듈) — RFC-0007 §4, Revalidation §6이 이미 유보했고, 이 ADC도
  결정하지 않는다. 실제 구현 착수 시점에 별도로 판단한다.
- "노출 + 무지시" vs "노출 + 최소 정책" 직접 비교 — 미실험.
- 저장소 규모 확장 시 AST 함수 후보 인덱스의 크기·정확도 — 미검증.
- RFC-0005(Development HQ ↔ Execution Layer Boundary)와의 불일치
  — RFC-0007 Open Issues에 이미 기록된 그대로 미해결이며 이 ADC의
  판단 대상이 아니다.

## Architecture / Contract 영향

- **Architecture Impact: NONE** — 판단 4가 재확인한 대로, 4개 판단
  항목 어느 것도 Jarvis OS Architecture Baseline이나 Development HQ
  Baseline의 어떤 문구도 변경을 요구하지 않는다. `hqs/development/
  BASELINE.md`는 MVP Implementation을 Baseline 범위에서 명시적으로
  제외하므로, 이 ADC의 Accept 4건 전부 Baseline Update 없이 MVP
  Implementation 범위 내에서 성립한다.
- **Contract Impact**: 함수 시그니처 변경 없음(RFC-0007 §3, §Contract
  Impact 원 판정 유지). 암묵적 입력 계약은 (Design 서술 + AST 함수
  후보 인덱스 + Exposure 정책 지시)의 3요소로 구체화된다 — 이는
  코드 수준 계약 변경이 아니라 Build 프롬프트 구성의 실질적 확장이며,
  실제 구현 시점에 워크플로 파일 docstring/주석으로 기록할 가치가
  있다(이 ADC가 그 기록을 지금 수행하지는 않는다).

## ADR 필요 여부

**전체 No ADR Required.** `hqs/development/BASELINE.md`가 "MVP
Implementation은 Baseline 범위가 아니다"라고 이미 명시했고, 4개
판단 모두 Architecture Impact NONE으로 확인됐다 — ADC-0004(Task
Dispatcher, Keep in MVP → No ADR Required)와 동일한 근거 구조다.
Governance Charter(`docs/governance/README.md`)의 흐름("ADC에서
Accept/Promote로 판단된 사항을 실제 Baseline 문서 변경 결정으로
기록"하는 것이 ADR의 역할)에 따르면, Baseline 문서 변경이 필요 없는
Accept는 ADR 없이 곧바로 구현으로 이어질 수 있다.

## Self Review

- Observation/Evidence만 사용했는가 — **Pass**. 4개 판단 모두
  RFC-0007, Revalidation 문서, 그리고 그 두 문서가 인용한 T06~T19
  Research 문서에 실제로 기록된 사실만 인용했다. 새 실험은 없다.
- Candidate가 정확히 4건인가 — **Pass**. 사용자가 제시한 4개 결정
  후보(Index, Closure, Exposure 정책, 기존 구조 유지)만 다뤘다.
- 구현을 설계했는가 — **No**. 함수 이름, 위치 확정, 실제 코드는
  이 문서에서 작성하지 않았다(판단 2가 위치를 명시적으로 유보).
- Architecture Drift가 없는가 — **없음**. 판단 4가 이를 명시적으로
  재확인했다.
- Kernel Leak가 없는가 — **없음**. Kernel/Runtime/Registry/Engine
  Gateway/Event Bus 어느 것도 이 문서가 다루지 않았다.
- Workflow/Agent/Model Freeze를 건드렸는가 — **아니오**. 4개 판단
  모두 기존 구조를 그대로 유지한 채 확장만 Accept했다.
- RFC-0007/Revalidation과 모순되지 않는가 — **Pass**. RFC-0007이
  ADC로 이관한 항목(§4 Context 생성 책임 위치)을 이 ADC도 동일하게
  유보했고, Revalidation의 권고(초기 범위 제한)를 판단 3에 그대로
  반영했다.
- Production Code를 수정했는가 — **아니오**. 이 문서는 판단만
  기록한다.
