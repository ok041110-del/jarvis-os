# Jarvis OS — Core Design Principles v1
> Reference Architecture v1의 후속 문서. 기술 선정 없이 순수 아키텍처/책임 정의만 다룸.

---

## 1. HQ Communication Policy

### 1-1. 세 가지 구조 비교

| 관점 | A. Gateway 강제 | B. Direct 허용 | C. Hybrid |
|---|---|---|---|
| **확장성** | Star 토폴로지 — HQ가 늘어도 새 HQ는 Gateway 하나만 알면 됨. 단, Gateway 자체가 트래픽 병목이 될 수 있음 (O(n) 부하 집중) | Mesh 토폴로지 — HQ 쌍이 늘수록 연결 조합이 O(n²)로 폭증. 관리 복잡도가 조직 규모에 비선형적으로 커짐 | 기본은 Star로 단순하게 유지, 트래픽이 실제로 몰리는 소수의 쌍만 선택적으로 mesh 추가. 조직 규모와 무관하게 복잡도를 통제 가능 |
| **보안** | 가장 강함 — 단일 진입점에서 모든 크로스-HQ 트래픽을 검사·필터링 | 가장 약함 — 각 HQ가 개별적으로 인증/인가를 구현해야 하고, 구현 수준이 HQ마다 달라 취약점이 생기기 쉬움 | Direct 채널도 Gateway가 사전 승인(allowlist)한 것만 허용 — 예외를 통제된 방식으로만 개방 |
| **권한 관리** | 중앙 일괄 관리, 정책 일관성 최고 | 분산 관리 — 정책이 HQ마다 다르게 적용되는 "policy drift" 위험이 실제로 발생하기 쉬움 | 정책 정의는 여전히 중앙(Jarvis OS)에 있고, "이 HQ 쌍은 Direct를 써도 된다"는 것도 그 정책의 일부로 관리됨 |
| **Audit** | 완벽 — 모든 크로스-HQ 통신이 한 지점을 지나므로 로그 커버리지 100% | 어려움 — 로그가 여러 HQ에 흩어져 통합 감사 추적(trace)이 힘듦 | Direct 채널 사용 시 Gateway에 이벤트를 비동기로 반드시 보고하도록 강제(shadow-log) — 성능은 Direct, 감사는 유지 |
| **Token 비용** | 상대적으로 높음 — 모든 요청이 Gateway를 거치며 컨텍스트 재해석/직렬화 오버헤드 발생 가능 | 가장 낮음 — 중간 hop 없이 직결 | 트래픽이 많은 핵심 쌍만 저비용 Direct로 처리, 나머지는 기본 경로 유지 — 전체 평균 비용이 가장 합리적 |
| **장애 대응** | Gateway가 단일 장애점(SPOF) — Gateway 장애 시 크로스-HQ 통신 전체 마비 (단, 개별 HQ의 자체 내부 동작은 유지됨) | 장애 지점이 N개로 분산 — 개별 장애의 파급력은 작지만, 어느 경로에서 실패했는지 추적이 어려워 디버깅 난이도가 오히려 높아짐 | Gateway 장애 시에도 사전 승인된 핵심 Direct 채널은 동작 지속 — 가장 회복력 있는 구조. 단 Direct 채널 자체의 장애 지점 수는 A보다 많음 |
| **구현 난이도** | 낮음~중간 — 라우팅 로직 하나만 잘 만들면 됨 | 높음 — 서비스 디스커버리, 개별 인증, circuit breaker 등을 각 HQ가 반복 구현해야 함 | 가장 높음 — 두 경로를 모두 지원하고 "언제 어느 경로를 쓸지" 판단하는 정책 엔진이 추가로 필요 |
| **장기 유지보수성** | 좋음 — 정책 변경 시 한 곳만 수정 | 나쁨 — HQ 수가 늘수록 관리해야 할 연결·정책의 수가 기하급수적으로 늘어남 | 초기 구현 비용은 가장 크지만, 시스템이 커질수록 유일하게 지속 가능한 방식 |

### 1-2. CTO 관점 추천

**결론: C (Hybrid)를 최종 목표로 하되, 실제 도입은 A → C 순서로 점진적으로 전환합니다.**

이유는 세 가지입니다.

1. **B는 사실상 배제합니다.** 지난 블루프린트 조사에서 확인했듯, "접근 제어를 각 애플리케이션 구현에 맡기면 팀이 늘수록 정책이 어긋난다"는 문제가 업계 전반의 공통 실패 패턴입니다. Jarvis OS처럼 HQ가 계속 늘어날 걸 전제로 한 시스템에서 B는 장기적으로 감당이 안 됩니다.
2. **처음부터 C를 완성형으로 구현하지 않습니다.** Jarvis OS의 Long-Term Thinking 원칙("10년을 기준으로 설계")은 "처음부터 다 만든다"가 아니라 "나중에 확장 가능한 형태로 시작한다"는 뜻입니다. HQ가 2~3개뿐인 초기 단계에서 Direct 채널 승인 체계까지 만드는 건 과설계입니다.
3. **전환 기준을 미리 정의해둡니다.** "특정 HQ 쌍의 Gateway 경유 트래픽이 일정 임계치를 넘거나, 레이턴시가 실사용에 영향을 줄 때"를 Direct 채널 승인 검토 트리거로 삼습니다. 이렇게 하면 최적화가 추측이 아니라 관찰된 병목에 대한 대응이 됩니다.

즉 **A로 시작하되, 처음부터 "Direct 채널을 나중에 꽂을 수 있는 구조(Hybrid-ready)"로 Gateway를 설계**하는 것이 핵심 결정입니다.

## 2. HQ Lifecycle (State Machine)

### 2-1. 상태 정의

| 상태 | 의미 | 리소스 유지 수준 |
|---|---|---|
| **Provisioning** | HQ가 레지스트리에 새로 등록되는 중. 아직 요청을 받을 수 없음 | 없음 |
| **Running** | 실제로 Division/Team이 Task를 처리 중인 활성 상태 | 최대 (Warm) |
| **Idle** | 프로세스는 떠 있지만 현재 처리 중인 Task 없음. 즉시 반응 가능 | 최소 유지 (Warm) |
| **Sleeping** | 리소스를 완전히 해제. 레지스트리에 정의(config)만 남아 있음 | 없음 (Cold) |
| **Disabled** | 정책 위반, 예산 초과, 보안 사고 등으로 **의도적으로** 비활성화됨 | 없음 |
| **Updating** | 정책/구성/모델 등이 갱신되는 중 | 진행 중인 Task는 drain(완료까지 허용) 또는 일시정지 |
| **Error** | 내부 오류로 정상 동작 불가 | 상태에 따라 다름 |
| **Decommissioned** | 영구 폐지 (조직 자체의 해체) | 없음 (레지스트리에서도 제거) |

### 2-2. 상태 전이 규칙

```
Provisioning ──(등록+헬스체크 통과)──▶ Idle
Idle ──(Task Dispatch 수신)──▶ Running
Running ──(마지막 Task 완료 + 일정 시간 무활동)──▶ Idle
Idle ──(정책 기준 장시간 무활동)──▶ Sleeping
Sleeping ──(Task Dispatch 또는 Event 매칭 또는 스케줄 트리거)──▶ Running   [Wake-up]
Running/Idle ──(구성 변경 트리거)──▶ Updating
Updating ──(갱신 완료)──▶ Idle
(모든 상태) ──(헬스체크 실패/예외 급증)──▶ Error
Error ──(자동 복구 성공 또는 사람 개입)──▶ Idle
(Disabled 제외 모든 상태) ──(정책 위반/예산 초과/수동 중지)──▶ Disabled
Disabled ──(사람의 명시적 재활성화만 가능)──▶ Idle
(Idle/Sleeping/Disabled) ──(폐지 결정)──▶ Decommissioned
```

**핵심 설계 결정 — Sleeping과 Disabled를 명확히 구분합니다.**

- **Sleeping**은 "일이 없어서 쉬는 것" → 누구나(이벤트든 요청이든) 깨울 수 있음
- **Disabled**는 "문제가 있어서 멈춘 것" → 자동으로 절대 깨어나지 않고, 사람의 명시적 승인만 재활성화 가능

이 구분이 없으면, 보안 사고로 멈춘 HQ가 자동화 로직에 의해 스스로 다시 깨어나는 사고가 발생할 수 있습니다. 회사로 치면 "퇴근한 직원"과 "정직 처분받은 직원"을 같은 방식으로 다루면 안 되는 것과 같습니다.

### 2-3. Wake-up 정책

| 트리거 | 대상 상태 | 동작 |
|---|---|---|
| Task Dispatch 도착 | Idle | 즉시 처리 (지연 없음) |
| Task Dispatch 도착 | Sleeping | Cold start 수행 (config 로드 → Division/Team 레지스트리 재구성 → Running 전이). **Wake-up latency budget을 명시적으로 정의해야 함** (예: N초 이내 미기동 시 장애로 간주) |
| 구독 중인 Event 매칭 | Sleeping | 위와 동일한 cold start 경로. Vision.md의 "명령 없이 백그라운드 자동화"가 실제로 여기서 구현됨 |
| 스케줄 트리거 (cron성) | Sleeping | 정해진 시각에 자체적으로 깨어남 (예: Personal HQ가 매일 오전 6시에 일정 점검) |
| 어떤 트리거든 | Disabled | **깨어나지 않음.** 요청은 거부되고, "Disabled 상태에서 접근 시도 발생"이라는 이벤트만 Jarvis OS에 보고 (감사 목적) |

## 3. 전 계층 State Model

| 계층 | Lifecycle 성격 | State Set | 상태 소멸/전이 조건 | 설계 근거 |
|---|---|---|---|---|
| **Jarvis OS** | Singleton, 상시(always-on) | `Running` / `Degraded`(일부 HQ 장애 중에도 전체는 정상) / `Maintenance` | 시스템 자체가 내려가는 것은 예정된 점검 외에는 없음 | OS 커널이 죽으면 전체가 멈추므로, 이 계층의 "상태"는 개별 Task가 아니라 시스템 전체 건강도를 뜻함 |
| **HQ** | 반영구, 조직형 | 2장 전체 (8개 상태) | 명시적 Decommission 결정 시에만 완전 소멸 | 회사 조직처럼 "존재는 계속하되 활동 강도가 변하는" 대상이므로 가장 정교한 상태기계가 필요 |
| **Division** | 유동적, HQ보다 가벼움 | `Active` / `Idle` / `Archived` | HQ가 Disabled/Decommissioned되면 하위 Division은 자동으로 Archived | HQ만큼 무거운 상태기계는 과설계. Division은 "프로젝트성 조직"에 가까워 3단계면 충분 |
| **Team** | **Task 단위, Ephemeral** | `Forming`(소집 중) → `Active`(실행 중) → `Completing`(결과 취합) → `Terminated`(소멸) | Task 종료 시 즉시 Terminated, 인스턴스 자체가 사라짐 (로그만 남음) | **Idle/Sleeping 상태를 의도적으로 두지 않음.** Team이 "쉬는 상태"를 갖는 순간 그건 사실상 상설 조직이 되어버려, "Task 단위 임시 작업반"이라는 철학이 무너짐. Team은 만들어지고, 일하고, 사라지는 것 외의 존재 방식이 없어야 함 |
| **Agent** | 호출 단위, 사실상 무상태(Stateless) | `Invoked` → `Completed` / `Failed` | 호출이 끝나면 그 즉시 인스턴스 개념 자체가 무의미해짐 | Agent는 "상태를 유지하는 존재"가 아니라 "실행 결과만 남기는 함수"에 가까움. 개인화가 필요하면 그건 Agent 자신의 상태가 아니라 외부 메모리 서비스에 위임 (Reference Architecture v1, 3-2 Agent 정의 참고) |

**표에서 읽어야 할 패턴**: 위 3개 계층(Jarvis OS, HQ, Division)은 "존재가 유지되며 활동 강도만 변하는" 상태기계이고, 아래 2개 계층(Team, Agent)은 "존재 자체가 생성·소멸하는" 이벤트에 가깝습니다. 이 경계선(Division과 Team 사이)이 Jarvis OS를 "조직"과 "작업"으로 나누는 실제 분기점입니다.

## 4. Event Bus의 책임 범위 (기술 중립)

Event Bus는 다음 책임만 가집니다. **그 이상은 갖지 않습니다** — 판단은 항상 Jarvis OS Gateway나 각 계층의 몫이고, Event Bus는 순수한 "배관"입니다.

| 책임 | 설명 |
|---|---|
| **Publish/Subscribe 통로 제공** | 어느 계층에서든 이벤트를 발행할 수 있고, 어느 계층에서든 구독할 수 있는 통로만 제공. "누가 무엇을 구독할 자격이 있는지"는 Event Bus가 판단하지 않음 — Jarvis OS 정책이 판단 |
| **계층 무관 전달** | 3장(Reference Architecture v1)에서 정의한 대로, Task Flow와 달리 인접 계층 규칙을 지키지 않고 어디서 어디로든 전달 가능해야 함 |
| **Wake-up 시그널의 통로** | Sleeping 상태의 HQ를 깨우는 이벤트가 지나가는 유일한 길목. Event Bus 자체가 "깨울지 말지"를 결정하지는 않고, 매칭된 이벤트를 전달만 함 — 깨울지 여부는 HQ의 구독 정책이 결정 |
| **Audit 원천 데이터 제공** | 모든 이벤트는 결국 감사 로그의 재료가 됨. Event Bus는 발생한 이벤트를 유실 없이 기록·전달할 책임은 있지만, 그 로그를 "감사 로그"로 가공하는 것은 별도 계층의 몫 |
| **전달 보장 수준 명시** | Task Flow처럼 엄격한 순서·정확성 보장은 필요 없음 (best-effort 허용). 다만 "적어도 한 번은 전달됨"(at-least-once) 수준은 책임져야 함 — 특히 Wake-up 트리거를 놓치면 자동화 자체가 실패하기 때문 |
| **격리(Isolation)** | 한 HQ에서 폭주한 이벤트가 다른 HQ의 이벤트 처리를 지연시키지 않아야 함. 구체적 구현(파티셔닝 등)은 기술 선정 단계의 몫이지만, "격리되어야 한다"는 요구사항 자체는 여기서 확정 |

**Event Bus가 하지 않는 것 (의도적 배제)**:
- 비즈니스 로직 판단 ("이 이벤트가 왔으니 Task를 만들어야 하는가"는 구독자인 HQ가 판단)
- 권한 검사 (누가 이 이벤트를 볼 수 있는지는 Jarvis OS Gateway의 정책)
- Task Flow 대체 (Event는 어디까지나 트리거일 뿐, Event 자체가 작업 지시서가 되지 않음 — Wake-up 후에는 반드시 정식 Task Dispatch로 전환)

## 5. 이번 문서에서 확정된 것 / 다음 결정 사항

**확정**:
- HQ 통신은 A(Gateway 강제)로 시작해 C(Hybrid)로 갈 수 있는 구조로 설계
- Sleeping(자동 wake 가능)과 Disabled(사람만 wake 가능)를 명확히 분리
- Team/Agent는 "쉬는 상태" 없이 생성-소멸만 존재 (조직 vs 작업의 경계 확정)
- Event Bus는 순수 배관 — 판단 로직을 갖지 않음

**다음 결정이 필요한 것**:
1. Direct 채널 승인 기준의 구체적 임계치 (트래픽량? 레이턴시? 누가 승인권자인가?)
2. Wake-up latency budget의 실제 숫자 (몇 초 안에 Cold start가 끝나야 정상인가)
3. Division의 Archived 상태에서 다시 Active로 돌아올 수 있는지 여부 (현재는 편도로 설계했는데, 재검토 필요할 수 있음)
