# DEV-HQ-V2.0 — Target File Exposure 완화 정책 Research

## 목적

RFC-0007의 두 번째 선행조건 — "기존 파일을 실제로 수정하는 Task에서는
Exposure가 구조적으로 불가피할 수 있고, 그 경우의 재작성 위험(T15/T16
누적 약 40%)을 완화할 정책이 없다" — 를 실제 Repository와 real
Engine으로 검증한다.

T12~T18은 전부 "기존 파일에 새 함수를 **추가**하는" Task였다. 이
문서는 처음으로 "기존 함수 하나를 **수정/확장**해야 하는" 실제
Task를 사용해, Target File Exposure가 진짜로 불가피한 상황에서 정책이
재작성 위험을 낮출 수 있는지 확인한다.

## 실험 설계

### 실제 Task

"`test_workflow_0002.py`의 `test_marker_not_on_last_line_is_treated_
as_having_issues` 함수가 마커가 한 번만 등장하는 경우만 다루는데,
마커가 두 번 등장하는 경우의 assertion이 빠져 있다. **새 테스트
함수를 만들지 않고 기존 함수 1개를 확장**한다." Design은 blind로
실행했다(실제 파일명을 issue에 언급하지 않음).

### 3개 조건

- **A. Target File 미노출**: Design + AST 발췌(Context)만 제공, 기존
  테스트 파일 내용은 보여주지 않음.
- **B. Target File 노출 + 변경 범위 명시**: 파일 전체를 보여주고,
  "오직 `test_marker_not_on_last_line_is_treated_as_having_issues`
  함수 본문 내부에만 추가한다. 다른 함수/import/공백은 어떤 이유로도
  변경하지 않는다"를 명시.
- **C. Target File 노출 + 기존 코드 보존 규칙 명시**: 파일 전체를
  보여주고, "이 파일의 모든 기존 코드를 한 글자도 바꾸지 않고 문자
  그대로 보존한다. 오직 지정된 함수 본문 내부에 코드만 추가한다"를
  명시(B보다 "보존"을 더 명시적으로 강조).

### Exposure 없이는 애초에 "수정"이 불가능하다

A는 재작성 위험이 확률적으로 발생한 것이 아니라, **Design의 요구사항
자체("기존 함수를 확장한다")를 구조적으로 충족할 수 없었다** — 파일을
보지 못하면 어떤 함수가 존재하는지, 그 함수가 정확히 무엇을 검증하는지
알 수 없으므로 새 함수를 만드는 것 외에 다른 선택지가 없었다. 이는
"위험이 낮다"가 아니라 "요구사항 미달성 100%"에 해당한다 — 실제 수정
Task에서 Exposure는 선택 사항이 아니라는 것을 보여주는 명확한
데이터다.

### B/C: 재작성이 발생해도 정확히 필요한 곳에만

B와 C 모두 파일 전체를 반환했지만(형식상 "전체 재작성"), 실제
diff(`diff` 명령으로 원본과 직접 대조)는 두 조건 모두 **지정된 함수
본문 안에 16줄이 순수하게 추가된 것뿐**이었다 — 다른 5개 함수, import,
공백은 문자 단위로 완전히 동일했다. "함수 개수가 늘지 않아야 한다"는
요구사항도 지켜졌다(원본 6개 테스트 함수 그대로, 새 함수 추가 없음 —
pytest 수집 결과 두 조건 모두 7개 항목 그대로).

### 내용 정확성 검증

두 조건이 추가한 assertion(`review_with_marker_twice`: 마커가 중간에
한 번, 마지막 줄에 한 번 등장 — 즉 마지막 줄이 marker인 경우)의 기대값을
실제 `_strip_trailing_marker` 구현으로 직접 확인했다: 마지막 줄이
정확히 marker와 일치하면 그 마커만 제거되고 원문의 나머지는 유지된다.
B/C가 작성한 assertion은 이 실제 동작과 일치했다(수동 트레이스로
확인 — Design이 우려했던 "기대 동작의 근거 부족" 리스크는 실제로는
발생하지 않았다).

두 조건을 실제 파일에 반영해(harness가 적용) pytest 실행:

```
14 passed in 0.03s
```

(B/C 각 파일 7개 테스트, 기존 6개 + 확장된 1개 함수 — 함수 개수 불변,
전부 통과.)

## Exposure Risk가 감소했는가

**감소했다고 판단한다 — 단, "재작성 발생 여부"가 아니라 "재작성이
발생했을 때 그 내용이 Scope를 지켰는가"를 기준으로.** T15/T16에서
측정한 "재작성 발생률(~40%)"은 이번 실험에서 유효한 지표가 아니다 —
실제 수정 Task에서는 노출된 상태에서 파일 전체를 반환하는 것 자체가
정상적인 응답 형식일 수 있기 때문이다(diff 형식을 강제하지 않는 한).
대신 이번 실험이 실제로 측정한 것은 **"노출 + 명시적 정책"이 있을 때
반환된 전체 파일의 diff가 Scope를 벗어나는가**이며, 답은 2/2(B, C)
모두 벗어나지 않았다.

## 최소 정책은 무엇인가

이번 1개 Task, 2개 조건(B, C)에서는 "변경 범위 명시"(B)와 "보존 규칙
명시"(C) 사이에 실질적 차이가 없었다 — 둘 다 완전한 Scope 준수를
보였다. 표본이 작아 "정확히 어느 문구가 결정적이었는지"는 이 Research로
분리할 수 없지만, 공통적으로 두 조건 모두 다음 두 요소를 포함했다:

1. **대상 함수를 정확한 이름으로 지목**(`test_marker_not_on_last_line_is_treated_as_having_issues`).
2. **"다른 부분은 건드리지 않는다"는 명시적 부정 지시**(B: "다른 함수/import/공백은 변경하지 않는다", C: "한 글자도 바꾸지 않고 보존한다").

이 두 요소를 포함한 노출이 최소 정책의 후보다. "노출만 하고 아무
지시도 주지 않는" 조건(T12/T13/T15/T16의 대부분)은 이번 Research의
비교 대상이 아니었으므로, 지시 유무 자체의 효과 차이는 이 문서만으로
확정할 수 없다(Open Issue).

## 최종 판정

**A. EXPOSURE RISK MITIGATED** — 실제 수정 Task에서 노출은 불가피하지만
(A 조건이 이를 구조적으로 증명), "대상 함수 명시 + 다른 부분 불변
명시"라는 최소 정책을 노출과 함께 제공하면 반환된 전체 파일의 diff가
Scope를 정확히 지켰다(2/2). 표본이 1개 Task, 2개 조건뿐이라 일반화에는
한계가 있지만, RFC-0007이 요구한 "정책 하나"의 존재 자체는 이번
Evidence로 뒷받침된다.

## RFC-0007에 미치는 영향

RFC-0007의 두 선행조건이 모두 최소 1건씩의 긍정적 Evidence를
얻었다: (1) 시작점 자동 식별 — AST 함수 후보 인덱스로 3/3 성공(T17,
이전 Research), (2) Exposure 위험 완화 — "대상 함수 명시 + 보존 규칙
명시" 정책으로 2/2 Scope 준수(이 문서). RFC-0007의 Decision(B.
CONDITIONAL)을 A(INTEGRATION JUSTIFIED)로 재평가할 근거가 마련됐다 —
다만 이 문서 자체는 그 재평가를 결정하지 않는다(RFC 재검토는 별도
절차).
