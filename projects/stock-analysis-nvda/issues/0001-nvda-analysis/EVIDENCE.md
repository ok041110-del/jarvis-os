# Evidence — NVDA Stock Dogfooding (실행 1회차)

PRD v1.2 8장 관찰 항목 기준. AAPL 실행(`../stock-analysis-aapl/issues/0001-aapl-analysis/EVIDENCE.md`)과
같은 형식으로, 이번 NVDA 실행에서 직접 관찰된 사실만 적는다. 아래 별도 절에서
두 실행을 비교한다.

## 업무 (Task)

- 5개 분석 → Bull/Bear → Synthesis → Final Report, 9회 `call_engine()` 순차
  호출이 AAPL과 동일한 구조로 수동 개입 없이 완주됐다.
- AAPL과 코드를 전혀 공유하지 않았음에도(각자 `projects/stock-analysis-*`에
  독립적인 `agents.py`) 동일한 지시문 패턴이 그대로 재사용 가능했다 — 프롬프트
  텍스트 자체가 도메인 일반적(회사명을 하드코딩하지 않음)이었기 때문.

## 역할 (Role)

- 5개 역할이 이번에도 서로 겹치지 않는 관점을 냈고, 각자 "제공 데이터 범위
  밖은 판단 불가"를 반복적으로 명시했다 — AAPL과 동일한 패턴.
- Industry Analyst가 이번에는 스스로 "이 출처들은 1차 공시나 IDC/Gartner
  같은 검증된 리서치가 아니다"라는 출처 신뢰도 비판까지 자발적으로 추가했다
  — AAPL의 Industry 분석에는 없던 문구다. 같은 지시문이라도 입력 데이터의
  출처 다양성/편차 크기(NVDA 쪽이 70~92%로 AAPL의 20~22%보다 훨씬 큼)에
  따라 Engine이 스스로 판단 수준을 조정한 것으로 보인다.

## 협업 (Collaboration)

- Synthesis가 이번에도 "합의된 사실 / 데이터 자체의 내적 불일치(bull·bear
  대립이 아님) / 같은 사실의 다른 해석(6가지) / 미해결 질문"을 구분했다 —
  AAPL Synthesis와 동일한 4단 구조가 자연 발생적으로(지시문에 이 4단 구조를
  명시하지 않았음에도) 반복됐다.
- NVDA Synthesis는 "데이터 자체의 내적 불일치"를 Bull/Bear의 해석 차이와
  명시적으로 분리하는 절을 따로 뒀다(AAPL은 이 구분이 본문에 섞여 있었음) —
  더 명확한 구조. 같은 지시문에서 더 나은 구조가 나온 사례로, 이 자체가
  Capability 지시문에 반영할 만한 개선 여지일 수 있으나, 1회 관찰만으로
  지시문을 바꾸지는 않는다(이론적 조정 금지 원칙).

## 시스템 (System)

- 회사 식별 문제(AAPL에서 발견)는 이번에 재발하지 않았다 — `raw_data.md`
  자체에 회사명을 명시하고 `runner.py`에 AAPL에서 검증된 `_COMPANY_HEADER`
  프리픽스를 재사용했기 때문. 두 가지 조치 중 어느 쪽이 결정적이었는지는
  이번 실행만으로 분리해서 확인할 수 없다(둘 다 동시에 적용했으므로).
- **새로 관찰된 것 — 출력 언어 비일관성**: AAPL 실행의 모든 산출물은
  한국어였고, NVDA 실행의 모든 산출물은 영어였다. 두 실행의 `raw_data.md`는
  둘 다 한국어 섹션 헤더/본문으로 작성됐고, `agents.py`의 지시문(영어)도
  동일했다 — 즉 입력 조건이 사실상 같은데 출력 언어가 실행마다 달랐다.
  하나의 실행 내부에서는 9개 산출물 전부가 일관되게 같은 언어였다(부분
  혼용은 없었음). 이는 Capability Contract가 출력 언어를 명시하지 않는다는
  사실(코드 리뷰 등 기존 Development HQ Capability도 동일)이 Investment
  도메인에서 처음으로 실제로 드러난 사례다. 최종 산출물 자체는 내적으로
  일관돼 있어 이번 실행을 망치지는 않았으므로, 지금 지시문을 수정하지
  않는다 — 반복 관찰되면 Capability 지시문에 언어 고정 여부를 추가할지
  검토할 후보로만 기록한다.
- Stop Trigger 미발동. Kernel/Registry/Scheduler 확장 불필요함을 다시 확인.

## AAPL ↔ NVDA 비교 (반복성 확인)

| 항목 | AAPL | NVDA | 반복 여부 |
|---|---|---|---|
| 9단계 파이프라인 완주 | 성공 | 성공 | **반복됨** |
| 새 Kernel/Registry/Scheduler 필요 | 없음 | 없음 | **반복됨** |
| Task 간 Context in-memory로 충분 | 예 | 예 | **반복됨** |
| Bull/Bear 대립 검토 유용성 | 확인(6가지 미해결 질문 도출) | 확인(6가지 미해결 질문 도출) | **반복됨** |
| Synthesis의 "합의/충돌/해석차/미해결질문" 4단 구조 | 자연 발생 | 자연 발생(더 명확한 절 분리) | **반복됨** |
| 회사 식별 문제 | 최초 발견, 수정 | 재발 안 함(수정 재사용) | **수정이 반복 재사용 가능함을 확인** |
| 산업 데이터 소스 편차 크기 | 좁음(20~22%대) | 넓음(70~92%) | 기업마다 다름 — Industry Capability는 편차 크기에 관계없이 동일한 지시문으로 대응함 |
| 출력 언어 | 한국어 | 영어 | **반복되지 않음** — 새로운 비일관성 발견 |
| Technical 분석의 정보 파편화(현재가 등) | 발생(Sentiment 섹션에만 현재가 있었음) | 미발생(raw_data.md TECHNICAL 섹션에 현재가 직접 포함) | 데이터 준비 방식에 따라 달라짐 — Capability 자체의 결함이 아니라 raw_data.md 작성 시점의 데이터 배치 문제였음을 재확인 |

**결론**: 역할 구조·Task 순서·협업 패턴(Bull/Bear/Synthesis)·시스템 요구사항
(Kernel 불필요, in-memory Context 충분)은 기업이 바뀌어도 그대로 반복됐다 —
이는 Development HQ 패턴이 특정 기업에 종속되지 않고 재사용 가능하다는
근거다. 반면 출력 언어는 반복되지 않았다 — 이는 Capability Contract가
아직 명시하지 않은 차원이며, Investment HQ가 실제로 여러 언어권 사용자를
대상으로 한다면 다뤄야 할 실제 요구사항 후보로 기록한다(지금 Architecture
변경을 트리거하지 않음 — 1회 관찰).
