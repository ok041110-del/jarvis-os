# Evidence — QQQ ETF Dogfooding (실행 1회차) — Stock/ETF 공통 요구사항 검증

PRD v1.2 관찰 항목 기준, Stock Team 4회 실행(`docs/research/STOCK-AGENT-SEPARATION-REVIEW-0001.md`)
과 동일한 형식. 이번 실행의 목적은 QQQ 분석 완성이 아니라, Stock과 ETF가
실제로 공유해야 하는 Capability가 있는지, ETF 고유의 새 요구사항이 있는지
검증하는 것이다.

## 업무 (Task)

- 11단계 파이프라인(7개 분석 → Bull/Bear → Synthesis → Final Report)이
  수동 개입 없이 완주됐다.
- `call_log.json` 실측: 11회 호출 합계 402.8초(약 6.7분). 7개 분석은
  17.7~31.8초/건, 입력 872~1,180자(Stock의 5개 분석 684~947자보다 다소
  큼 — Fund Header + ETF 섹션 데이터가 조금 더 길기 때문). Bull/Bear는
  각각 입력 20,155자(JPM의 10,479자 대비 약 2배 — 분석 축이 5개에서
  7개로 늘어난 만큼 누적 텍스트도 커짐). Final Report는 입력 41,567자,
  **소요 133.5초로 이번 실행에서 가장 오래 걸렸다**(JPM 최종 리포트는
  50.9초) — 뒤에서 자세히 다룸.

## 역할 (Role) — Stock 5개 분석의 재사용 가능성

**Stock의 5개 분석 역할을 그대로 재사용하지 않았다.** ETF 고유의 7개
분석 축을 새로 정의했다:

| Stock 5개 분석 | ETF에서의 대응 여부 |
|---|---|
| Fundamental(재무/마진) | 대응 없음 — ETF는 발행사 재무제표가 아니라 펀드 자체의 구성/비용 구조를 본다 |
| Technical(추세/모멘텀) | 부분 대응 — Performance/Volatility Analyst가 수익률·변동성을 다루지만 지지선/저항선 같은 개별 종목 기술적 지표 개념은 없음 |
| Industry/Competition(경쟁구도) | 부분 대응 — Sector/Geography Exposure Analyst가 섹터 집중도를 다루지만 "경쟁사 비교"가 아니라 "섹터 비중 자체"가 초점 |
| News/Event(정성적 이벤트) | 대응 없음 — 이번 실행에서는 Macro Analyst가 대신 다뤘으나 개별 이벤트가 아니라 거시 시나리오 중심으로 성격이 다름 |
| Sentiment(애널리스트 컨센서스) | 대응 없음 — ETF에는 개별 종목 같은 애널리스트 목표주가 컨센서스 개념 자체가 없음 |

**ETF에서 새로 필요해진 역할 3개**(Stock에 대응 항목이 아예 없음):

- **Composition/Index Analyst** — 추적지수·가중방법론·리밸런싱은 개별
  주식에는 존재하지 않는 개념.
- **Cost/Tracking Analyst** — 총보수율·추적오차는 펀드 고유 개념. 이번
  실행에서 추적오차 수치 자체가 자료에 없다는 사실을 스스로 명시하는
  등, Stock의 "데이터 한계 인정" 패턴이 ETF 고유 개념에도 그대로
  적용됨을 확인했다.
- **Distribution Analyst** — Stock의 Sentiment/Fundamental과 달리, 배당
  주기·분배금 추이 자체가 분석 대상인 역할. (개별 주식도 배당이 있지만
  Stock Team 4회 실행에서는 별도 역할로 다루지 않았음 — Fundamental
  분석 안에 부분적으로만 언급됨.)

**결론**: Stock의 5개 분석 역할은 ETF에서 그대로 유효하지 않다. 개념적
유사성(수익률/변동성 ≈ Technical, 섹터 집중도 ≈ Industry)은 있으나
실제 프롬프트나 함수를 그대로 재사용할 만큼 동일하지 않았다 — 이번
실행에서 실제로 재사용을 시도하지 않고 처음부터 별도로 작성한 것 자체가
이 판단의 근거다.

## 협업 (Collaboration) — Bull/Bear/Synthesis 4단계의 구조적 유사성

- Bull/Bear/Synthesis/Final Report 4단계는 Stock과 **구조적으로 매우
  유사**했다: "N개 분석 보고서를 근거로 낙관/비관 사례 구성 → 사실
  합의/해석차/데이터 불일치/미해결질문으로 종합"이라는 패턴이 그대로
  나타났다. Synthesis는 이번에도 "사실 자체의 충돌은 없음(no factual
  dispute)", 순수 해석 차이(집중도를 우위로 볼지 리스크로 볼지)만
  존재한다고 명시했다 — JPM에서 처음 관찰된 유형("순수 해석 차이만
  존재")이 ETF 도메인에서도 재현됐다.
- **다만 이 4단계가 실제로 코드/Capability를 공유하지는 않았다** —
  `projects/etf-analysis-qqq/agents.py`는 Stock의 어떤 함수도 import하지
  않고 처음부터 새로 작성됐다. 구조적 유사성은 "같은 패턴을 다시 손으로
  작성했다"는 뜻이지 "실제로 공유했다"는 뜻이 아니다.

## Context 규모/전달 방식 — Stock 대비 실측 비교

| 항목 | Stock(JPM, 5개 분석) | ETF(QQQ, 7개 분석) |
|---|---|---|
| 분석당 입력 | 684~947자 | 872~1,180자 |
| Bull/Bear 입력 | 10,479자 | 20,155자(약 1.9배) |
| Synthesis 입력 | 15,817자 | 15,315자(비슷함 — Bull/Bear 출력 자체 길이는 유사) |
| Final Report 입력 | 32,270자 | 41,567자(약 1.3배) |
| Final Report 소요시간 | 50.9초 | **133.5초(약 2.6배)** |
| 9~11단계 합계 소요 | 313초 | 402.8초 |

**Context 규모는 분석 축 개수(5개→7개)에 비례해 커졌고, 전달 방식
자체(in-memory 문자열 결합)는 동일하게 충분했다.** 다만 Final Report
소요시간이 입력 크기 증가폭(1.3배)보다 훨씬 큰 폭(2.6배)으로 늘어난
점은 주목할 만하다 — 출력 길이도 12,808자→19,709자로 늘었으므로,
소요시간 증가가 입력 길이보다 출력 길이(더 많은 섹션을 통합 서술해야
함)와 더 강하게 연관되어 보인다. `call_engine()`의 `timeout=180`
(development-hq/mvp/engine.py) 대비 133.5초는 아직 여유가 있으나,
분석 축이 더 늘어나는 시나리오(예: ETF+개별 구성종목까지 통합 리포트)
에서는 이 마진이 줄어들 수 있다 — **다만 이는 이번 실행에서 실제로
발생한 문제가 아니라 추세 관찰이며, 지금 Runtime/Timeout 조정이
필요하다는 근거는 아니다.**

## Cache 필요성

**발생하지 않았다.** 이번 실행에서 동일 데이터나 동일 Prompt가 반복
호출된 적이 없다(11개 호출 전부 서로 다른 지시문·데이터). Stock 4회와
동일하게 in-memory 1회성 전달로 충분했다. 향후 QQQ를 정기적으로
재분석하게 되면 같은 raw_data 구조가 반복될 가능성은 있으나, 이는 이번
1회 실행에서 실제로 관찰된 필요가 아니라 추정이므로 지금 Cache를
설계하지 않는다.

## 병렬 실행 필요성

**이번 실행은 검증하지 않았다(불필요를 확인한 것이 아니라,애초에
시도하지 않았다).** 사용자 지시에 따라 ETF 1개만 선정했고, 여러 ETF나
ETF 구성종목(예: QQQ 상위 10개 보유종목 각각) 단위의 처리는 이번 범위
밖이었다. 따라서 "병렬 실행이 불필요함을 확인"이라고 말할 수 없다 —
Stock 4회의 "불필요 확인"과 이번 ETF의 "미검증"은 다른 상태이며, 이
차이를 그대로 기록한다.

## 정기 데이터 갱신 — Runtime/Automation 필요성

**발생하지 않았다.** 이번 실행도 Stock과 동일하게 이 세션이 WebSearch로
1회 수동 수집한 스냅샷(`raw_data.md`)을 사용했다. Composition 분석에서
"분기별 리밸런싱"이 언급되어 ETF가 개념적으로 주기적 데이터 갱신과
연관이 있다는 힌트는 있었으나, 이번 1회 실행에서 실제로 자동 갱신이
필요했던 지점은 없었다 — 이론적 가능성과 실제 발생을 구분해 기록한다.

## 시스템 (System)

- Stop Trigger 미발동. Kernel/Registry/Scheduler 확장 불필요함이 ETF
  도메인에서도 재확인됐다.
- 데이터 불일치 인정 패턴(Stock 4회에서 반복 확인)이 ETF에서도 그대로
  나타났다: 보유종목 비중(3개 소스 불일치), 섹터 비중(57.8%/64.75%/
  66.9% 불일치), 추적오차 수치 부재를 각 역할이 스스로 명시했다.
- 출력 언어: 이번 실행은 Composition/Holdings/Performance/Exposure/
  Bull/Bear/Synthesis가 영어, Cost/Macro가 한국어로 나뉘었다(단일 실행
  내 혼재 — MSFT에서 처음 관찰된 패턴과 동일 성격). 5회째 실행에서도
  출력 언어는 여전히 비결정적이다.

## 공통 Capability 후보 판정

사용자 지시 8~9번("실제 반복된 공통 요구사항만 기록", "재사용
가능해 보인다는 이유만으로 만들지 않는다")에 따라 판정한다.

**공통 Capability 후보: 없음(이번 실행 기준).** Bull/Bear/Synthesis/
Final Report 4단계가 구조적으로 유사한 패턴을 보였으나:
1. 이는 ETF Dogfooding **1회차**의 관찰이다 — Stock Team이 승격 전
   3회 반복을 요구했던 것과 같은 기준을 적용하면, ETF는 아직 반복
   자체가 없다(1/1).
2. 실제 코드 공유는 이번에도 시도되지 않았다(project-local 원칙을
   그대로 따름) — "공유가 가능해 보인다"는 관찰과 "공유가 실제로
   필요하다"는 결론은 다르다.
3. Stock의 5개 분석 역할은 ETF에서 재사용되지 않았고, ETF는 3개의
   완전히 새로운 역할(Composition/Cost/Distribution)을 필요로 했다 —
   이는 오히려 도메인별 특화가 필요하다는 근거에 가깝다.

Bull/Bear/Synthesis/Final Report의 구조적 유사성은 **향후 재평가
후보로만 기록**한다(ETF Dogfooding이 2회 이상 반복되고, 그때도 동일한
유사성이 재확인되면 재검토).

## 관찰되지 않은 것 (명시적으로 기록)

- 여러 ETF 간 비교, ETF 구성종목 단위 개별 분석 — 이번 범위 밖.
- Cache/Runtime/Automation이 실제로 필요해지는 시점 — 1회 실행에서는
  나타나지 않았다.
- Stock과 ETF의 실제 Capability 공유 — 시도되지 않았고, 필요도
  관찰되지 않았다.
