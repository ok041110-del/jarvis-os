# Evidence — JPM Stock Dogfooding (실행 1회차) — 역할/Agent 분리 검증

PRD v1.2 8장 관찰 항목 기준, `docs/research/STOCK-TEAM-DEFINITION-0001.md`
승격 이후 첫 실행. AAPL/NVDA/MSFT EVIDENCE.md와 같은 형식이되, 이번 실행은
"역할/Agent 단위 분리가 실제로 필요한가"라는 별도 질문에 답하기 위해
각 역할의 입력/출력/소요 시간을 `call_log.json`으로 추가 계측했다.

## 업무 (Task)

- 9단계 파이프라인이 이번(4회차)에도 수동 개입 없이 완주됐다(회사 식별
  수정 `_COMPANY_HEADER` 재사용, 재발 문제 없음).
- `call_log.json` 실측(9회 호출 합계 313초, 약 5.2분): 5개 분석은
  16.7~38.4초/건, 입력 684~947자·출력 1,533~2,971자로 서로 비슷한
  규모였다. Bull/Bear는 각각 입력 10,479자(5개 분석 전체 이어붙임)에
  34.9초/45.2초. Synthesis는 입력 15,817자(Bull+Bear)에 33.2초. Final
  Report는 입력 32,270자(8개 산출물 누적)에 50.9초로 가장 컸다 — 입력이
  누적될수록(파이프라인 뒤로 갈수록) 소요 시간도 대체로 늘어났으나,
  9회 전체가 6분 이내로 끝나 병렬 실행이 필요하다는 근거는 이번에도
  나타나지 않았다.

## 역할 (Role) — 입력·출력·Context 의존성 실측

| 역할 | 입력(자) | 출력(자) | 소요(초) | Context 의존성 |
|---|---|---|---|---|
| Fundamental Analyst | 819 | 1,914 | 38.4 | `raw_data.md`의 자기 섹션만 |
| Technical Analyst | 684 | 2,971 | 16.7 | 〃 |
| Industry Analyst | 748 | 1,544 | 31.2 | 〃 |
| News/Event Analyst | 947 | 2,402 | 36.7 | 〃 |
| Sentiment Analyst | 746 | 1,533 | 25.8 | 〃 |
| Bull Researcher | 10,479 | 6,799 | 34.9 | 위 5개 분석 결과 전체 |
| Bear Researcher | 10,479 | 9,018 | 45.2 | 위 5개 분석 결과 전체(Bull과 동일 입력) |
| Synthesis | 15,817 | 6,089 | 33.2 | Bull + Bear |
| Report Writer | 32,270 | 12,808 | 50.9 | 8개 산출물 전체 누적 |

- 5개 분석 역할은 서로 겹치지 않는 관점을 유지했다: Fundamental(헤드라인
  EPS $7.70 vs 조정 EPS $6.14 괴리 지적), Technical(저항선 근접+RSI 63
  경계 신호), Industry(시장점유율 수치 부재를 스스로 한계로 명시),
  News/Event(Dimon 발언 3건을 리스크관리/지정학/승계 3축으로 분리),
  Sentiment(목표주가 3개 소스 간 $39 괴리를 핵심 리스크로 지목) — AAPL/
  NVDA/MSFT와 동일하게 "제공 데이터 범위 밖은 판단 불가"가 반복됐다.
- **NVDA에서 처음 관찰된 "자발적 출처 신뢰도 비판"이 4번째로도 재현됨**:
  Industry Analyst가 "시가총액 순위의 비교 대상군과 산정 방법론이
  명시되지 않았다", "경쟁사 시장점유율 수치가 없다"고 스스로 지적했다 —
  AAPL에는 없던 패턴이 NVDA·MSFT·JPM 3회 연속 나타남(각기 다른 정도로).
- **정보 파편화 문제(AAPL에서 최초 발견) 재발 없음**: `raw_data.md`
  자체에 현재가·회사명이 포함되어 있어 Technical 분석이 현재가를 정상
  참조했다 — NVDA/MSFT에 이어 3회 연속 미발생.

## 협업 (Collaboration) — Bull/Bear/Synthesis

- Bull/Bear 대립 검토가 4번째로도 유용했으나, **이번에는 이전 3회와 질적
  으로 다른 패턴이 나타났다**: Synthesis가 "두 진영 사이에 사실 자체의
  충돌은 사실상 없다(no factual contradiction)"고 명시했다 — 같은 5개
  숫자·사실을 정확히 공유하면서 해석(가이던스 상향의 의미, RSI 63의 의미,
  공동 President 체제의 의미)만 갈렸다. AAPL(산업 통계 1건 실제 충돌),
  MSFT(Azure 번들링의 이중적 사실)에서는 최소 1건의 실제 사실 차원
  충돌/이중성이 있었던 것과 달리, JPM은 순수 해석 차이만으로 구성된
  최초 사례다 — Bull/Bear 유용성이 "사실 대립"이 아니라 "동일 사실의
  대립적 해석"만으로도 유지될 수 있음을 보여준다.
- Synthesis의 "합의된 사실/순수 해석차/데이터 자체의 불일치(목표주가
  분산, 표본 불일치, CAGR 범위 모호성)/미해결 질문" 4단 구조가 이번에도
  자연 발생적으로 나타났다(AAPL/NVDA와 동일 구조, 지시문에 명시하지 않음).
- Context는 이번에도 in-memory 변수(문자열 결합)만으로 4/4 충분했다.

## 시스템 (System)

- Stop Trigger 미발동. Kernel/Registry/Scheduler 확장 불필요함이 4번째로
  재확인됐다.
- **출력 언어**: 이번 실행은 9개 산출물 전부가 영어였다(AAPL=전체 한국어,
  NVDA=전체 영어, MSFT=혼재, JPM=전체 영어) — 4회 중 2회가 "전체 영어"로
  나타나 여전히 비결정적이다.
- **새로 관찰된 것 — 부분 언어 누출**: `bear_case.md` 25행에
  "sasang choego"(한국어 "사상 최고"의 로마자 표기)가 영어 문장 안에
  그대로 섞여 나타났다. `raw_data.md`가 한국어로 작성됐고
  (`Company: ... 사상 최고 수준` 표현이 원문에 있었음), 출력 지시는
  영어였는데, 번역 대신 발음 그대로 로마자 전사가 일어난 사례다. 이는
  기존에 기록된 "출력 언어 비결정성"(문서 단위/실행 단위 비결정성)과는
  다른 새로운 하위 현상(단일 실행 내 부분 토큰 누출)이며, 지금 지시문을
  수정하지 않고 기존 Capability 개선 후보에 하위 항목으로만 추가한다.

## 역할/Agent 분리 필요성 — 지시된 7개 관찰 항목에 대한 답

1. **같은 역할을 독립적으로 반복 호출할 필요가 있는가?** — 아니다. 4회
   실행(AAPL/NVDA/MSFT/JPM) 모두 각 역할이 정확히 1회씩만 호출됐다.
2. **한 역할의 결과를 다른 역할이 지속적으로 재사용하는가?** — 그렇다.
   `call_log.json`이 이를 정량적으로 보여준다: Bull/Bear는 5개 분석
   전체(10,479자)를, Synthesis는 Bull+Bear(15,817자)를, Report는 8개
   산출물 전체(32,270자)를 누적 재사용한다. 다만 이 재사용은 **순방향
   누적 텍스트 결합**이며, 어떤 역할도 이전 역할을 "다시 호출"하거나
   "선택적으로 호출"하지 않는다 — `docs/research/EVIDENCE-REVIEW-0001.md`
   가 Development HQ SDLC에서 관찰한 Artifact Flow(상위 산출물이 하위에
   verbatim 포함되는 패턴)와 성격이 같다.
3. **역할별 전문 지시가 실제 품질 차이를 만드는가?** — 그렇다. 5개
   분석은 동일한 원본 데이터를 공유하면서도 서로 다른 축(재무/기술적
   지표/경쟁구도/이벤트/시장심리)에서 서로 다른 리스크를 지적했다 —
   4회 모두 반복 확인.
4. **하나의 Agent가 여러 역할을 맡는 것보다 분리하는 것이 실제로
   유리한가?** — 부분적으로만 확인된다. 역할별로 "자기 영역만 판단"이라는
   정직성 유지에는 유리함이 4회 반복 확인됐다. 그러나 이번 실행에서도
   각 역할은 프로젝트별로 독립적으로 복제된 **project-local 함수**일
   뿐, 실제로 여러 Workflow/Team이 "같은 Agent 인스턴스"를 공유해 호출한
   사례는 아직 없다(`textkit`/`notekeeper`/AAPL/NVDA/MSFT/JPM 각각
   자기만의 `agents.py` 사본을 가짐). 즉 "역할 분리"의 이점은 반복
   확인됐지만, "Agent로 등록해 여러 곳에서 공유 재사용"의 이점은 이번
   실행 범위에서 검증되지 않았다.
5. **역할 간 병렬 실행이 실제로 필요한가?** — 아니다. 9회 호출 합계
   313초로 성능 문제가 없었다(4/4 실행 모두 순차 실행으로 충분).
6. **역할을 독립 Agent로 등록해야 할 만큼 반복성과 독립성이 있는가?** —
   아래 "판정" 절 참조.
7. (병렬/재사용 외 추가 관찰) 5개 분석 역할의 입력·출력 크기가 서로
   비슷한 규모(수백~수천 자)였던 반면, Bull/Bear→Synthesis→Report로
   갈수록 입력이 기하급수적으로 커졌다(819자 → 32,270자) — 이는 역할
   자체의 복잡도 차이라기보다 **누적 구조의 자연스러운 결과**로 보인다.

## 판정 — Agent 승격 후보 vs 보류

사용자 지시의 판정 기준을 8개 업무 각각에 적용한다.

| 업무 | 동일 역할 반복(4/4) | 독립 입출력 경계 | 명확한 전문 목적 구분 | 독립 실행/재사용 가치 실제 확인 | 판정 |
|---|---|---|---|---|---|
| Fundamental Analyst | ✓ | ✓(raw_data 자기 섹션만) | ✓ | ✗(공유 재사용 미검증) | **보류** |
| Technical Analyst | ✓ | ✓ | ✓ | ✗ | **보류** |
| Industry/Competition Analyst | ✓ | ✓ | ✓(+ 자발적 출처 비판 2/4 확인) | ✗ | **보류** |
| News/Event Analyst | ✓ | ✓ | ✓ | ✗ | **보류** |
| Sentiment Analyst | ✓ | ✓ | ✓ | ✗ | **보류** |
| Bull Researcher | ✓ | △(5개 분석 전체에 의존, 자체 입력 경계는 없음) | ✓(Bear와 대칭 구분) | ✗ | **보류** |
| Bear Researcher | ✓ | △ | ✓ | ✗ | **보류** |
| Synthesis | ✓ | ✗(Bull+Bear 결과에 전적으로 의존) | ✓ | ✗ | **보류(가장 강결합)** |
| Final Report | ✓ | ✗(8개 산출물 전체 누적 의존) | ✓(통합·정규화 역할) | ✗ | **보류(가장 강결합)** |

**8개 업무 전부 이번 실행 기준 "Agent 승격 보류"로 판정한다.** 판정
근거:

- 4개 판정 기준 중 "독립 실행/재사용 가치가 실제로 확인됨"이 8개 업무
  어디에서도 충족되지 않았다 — 모든 재사용은 project-local 코드 복제를
  통한 것이며, 실제로 하나의 Agent를 여러 Workflow/Team이 공유 호출한
  사례가 한 번도 없다(AGENT_CAPABILITY_MAP이 project마다 독립적으로
  존재).
- "단순 Prompt 단계에 불과함"(보류 기준)은 아니다 — 4회 반복에서 역할별
  전문성 차이가 실제로 관찰됐다. 그러나 "1회성 작업"도 아니다(4회
  반복). 즉 8개 업무는 [승격 후보]와 [보류] 두 판정 기준 세트 중 어느
  쪽에도 완전히 속하지 않는 중간 지대에 있으며, 이 경우 사용자 지시
  9번("단순히 역할 이름이 존재한다는 이유로 Agent를 만들지 않는다")에
  따라 보수적으로 보류로 판정한다.
- 다만 5개 분석 역할(Fundamental/Technical/Industry/News-Event/Sentiment)
  은 독립 입출력 경계와 전문성 구분이 가장 뚜렷해, 향후 재평가 시
  가장 유력한 후보 그룹으로 남긴다. Bull/Bear/Synthesis/Report는 누적
  의존 구조가 강해 후보 그룹에서도 후순위다.

## 관찰되지 않은 것 (명시적으로 기록)

- 역할을 독립적으로(파이프라인 밖에서) 호출해야 하는 실제 필요 — 4회
  모두 관찰되지 않았다.
- 동일 Agent를 여러 프로젝트/Workflow가 공유 호출하는 사례 — 관찰되지
  않았다(모든 재사용이 코드 복제).
- 병렬 실행이 실제로 필요해지는 시점 — 4회 모두 순차 실행으로 성능
  문제 없이 완료됐다.
