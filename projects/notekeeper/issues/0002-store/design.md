# Design: Add NoteStore (JSON-file persistence) to notekeeper

## NoteStore 설계안

### 1. 접근 방식

`NoteStore`는 `Note` 컬렉션의 **인메모리 캐시 + 명시적 디스크 동기화**를 책임지는 얇은 계층으로 설계한다. 직렬화 규칙은 전적으로 `Note.to_dict()`/`Note.from_dict()`에 위임하고, `NoteStore`는 순수하게 "컬렉션 관리 + 파일 I/O 오케스트레이션"만 담당한다. 이 경계를 지키는 게 핵심 설계 원칙이다 — `NoteStore`가 `Note`의 필드를 직접 들여다보거나 조작하지 않는다.

파일 포맷은 최상위가 JSON 배열인 단순 구조로 한다: `[note.to_dict(), note.to_dict(), ...]`. 메타데이터 래퍼(`{"version": 1, "notes": [...]}`)는 요구사항에 없으므로 넣지 않는다 — 필요해지면 그때 마이그레이션을 고려한다.

### 2. 내부 자료구조

리스트가 아니라 `dict[str, Note]` (id → Note, 삽입 순서 보존)로 내부 상태를 관리할 것을 제안한다. 이렇게 하면:
- `get`/`delete`가 O(1)
- `add`의 id 중복 정책이 자연스럽게 "덮어쓰기(upsert)"로 정해짐 — 같은 키에 새 값을 넣으면 교체되는 dict의 기본 동작을 그대로 쓰는 것이므로 별도 분기 로직이 필요 없다. 에러를 던지는 정책보다 구현이 단순하고, "추가"와 "갱신"을 분리하지 않기로 한 요구사항 범위(수정 API가 명시적으로 없음)와도 맞는다.
- `list()`는 `list(self._notes.values())`로 **새 리스트 객체**를 반환한다. `Note` 인스턴스 자체는 공유되지만(얕은 복사), 반환된 리스트를 외부에서 append/remove 해도 내부 dict는 오염되지 않는다. Note 객체의 필드를 외부에서 직접 변경하는 것까지는 막지 않는다 — 이건 `Note`의 불변성 문제이지 `NoteStore`의 책임 밖으로 본다.

### 3. 메서드별 동작 확정

- **`__init__(path)`**: `path`를 `Path(path)`로 통일해 보관. 파일이 존재하면 `load()` 호출, 없으면 빈 dict로 시작 — 예외 없음(요구사항대로).
- **`add(note)`**: `self._notes[note.id] = note` 후 즉시 `save()`. 중복 id는 조용히 덮어씀(위 3항 참조).
- **`get(note_id)`**: `self._notes.get(note_id)` — 없으면 `None`.
- **`delete(note_id)`**: id 존재 시 제거 + `save()` + `True` 반환. 없으면 `False` 반환, 파일 쓰기 없음(불필요한 I/O 방지).
- **`list()`**: 위에서 설명한 얕은 복사 리스트 반환.
- **`save()`**: 현재 메모리 상태를 JSON으로 직렬화해 파일에 기록. 원자적 쓰기 적용(4항 참조).
- **`load()`**: 파일을 읽어 `Note.from_dict()`로 역직렬화하고 **메모리 상태를 완전히 대체**(merge 아님). 외부에서 `load()`를 재호출하면 미저장 변경사항은 유실된다 — 이는 "명시적 재로드는 곧 디스크를 신뢰 소스로 취급하겠다는 의도"로 해석하고 그렇게 문서화한다. 필요하면 호출부가 먼저 `save()`하면 되므로 `NoteStore`가 알아서 막을 필요는 없다.

### 4. 원자적 쓰기 — 채택 권장

`save()`는 `path`에 직접 쓰지 않고, 같은 디렉터리에 임시 파일(`path.with_suffix(path.suffix + ".tmp")` 등)을 쓴 뒤 `os.replace()`로 원래 경로에 원자적으로 교체한다. 표준 라이브러리(`pathlib` + `os`)만으로 가능하고, 리스크 4번(부분 쓰기로 인한 파일 손상)을 실질적으로 제거하는 반면 구현 비용은 낮다. 요구사항에 명시되지 않았지만 "손상된 JSON을 명확한 예외로 다뤄야 한다"는 요구와 상충하지 않게 하려면 애초에 손상이 발생하지 않도록 막는 이 방식이 더 견고하다고 판단, 채택을 제안한다.

### 5. 에러 처리 정책

손상 파일과 관련된 모든 케이스(`json.JSONDecodeError`, `Note.from_dict()`에서 나는 `KeyError`/`TypeError` 등 필수 키 누락)를 `load()` 내부에서 **하나의 커스텀 예외 `NoteStoreError`로 감싸서 재발생**시킨다(`raise NoteStoreError(...) from original`). 원본 예외 타입을 그대로 흘려보내는 대신 커스텀 예외로 통일하는 이유:
- 호출부가 "저장소 계층 문제"인지 "우연히 같은 이름의 다른 JSONDecodeError"인지 구분할 필요 없이 한 가지 타입만 잡으면 됨
- `from e` 체이닝으로 원인 정보(트레이스백, 원본 메시지)는 보존되므로 디버깅 정보 손실 없음
- 메시지에 파일 경로를 포함시켜 "어느 파일이 문제인지" 즉시 알 수 있게 함

파일/디렉터리 권한 문제(`PermissionError`, `OSError`)는 감싸지 않고 그대로 전파한다 — 이건 저장소 로직의 문제가 아니라 환경 문제이므로 원래 예외 타입이 더 정보가 많다.

### 6. 책임 경계 요약

| 책임 | 담당 |
|---|---|
| Note 필드 검증/직렬화 규칙 | `Note` (기존 코드, 변경 없음) |
| 컬렉션 관리(추가/조회/삭제/목록) | `NoteStore` |
| 파일 I/O, 원자적 쓰기 | `NoteStore` |
| 손상 데이터 예외 변환 | `NoteStore.load()` |

### 7. 리스크 및 트레이드오프 (남는 것들)

- **O(n) 전체 재작성**: `add`/`delete` 매번 전체 파일을 다시 씀. 요구사항상 허용 범위이고, 원자적 쓰기와도 잘 맞는 방식(부분 갱신을 시도하지 않으므로 로직이 단순함)이라 지금 단계에서는 문제 삼지 않는다. 노트 수가 매우 커지면 다음 단계에서 append-log나 DB 전환을 고려할 사안.
- **동시성 미지원**: 파일 락 없음. 단일 프로세스 사용을 전제로 하며, 멀티프로세스 동시 접근 시 마지막 쓰기가 이긴다(원자적 쓰기 덕분에 손상은 안 되지만 갱신 유실 가능). 요구사항 범위 밖으로 명시되어 있으므로 이번 설계에는 포함하지 않음.
- **`NoteStoreError` 도입 자체가 새 공개 API**: 테스트/호출부가 이 예외 타입에 의존하게 되므로, 이름과 위치(`store.py` 내 정의)를 이번에 확정하고 이후 변경하지 않는 게 좋다.

이 설계로 진행해도 괜찮을지, 특히 (a) dict 기반 upsert 정책 (b) 원자적 쓰기 채택 (c) `NoteStoreError` 통일 세 가지 결정에 동의하는지 확인 후 구현으로 넘어가면 됩니다.
