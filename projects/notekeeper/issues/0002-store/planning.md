# Planning: Add NoteStore (JSON-file persistence) to notekeeper

## 요구사항 분석: NoteStore (JSON 파일 기반 영속 저장소)

### 목표
`notekeeper`에 메모리상의 `Note` 객체 컬렉션을 JSON 파일에 영속화하는 `NoteStore` 클래스를 `store.py`에 추가한다. 기존 `Note.to_dict()`/`Note.from_dict()`를 재사용하여 직렬화 로직 중복 없이 CRUD(추가/조회/삭제/목록)와 명시적 save/load를 제공하는 것이 핵심 목표다.

### 범위
**포함:**
- `NoteStore.__init__(path)`: 경로 보관 + 파일 존재 시 자동 `load()`, 없으면 빈 상태로 시작(예외 없음)
- `add(note) -> None`: 메모리 반영 + 즉시 `save()` (디스크 동기화 보장)
- `get(note_id) -> Note | None`: 없으면 None (예외 없음)
- `delete(note_id) -> bool`: 성공 여부 반환 + 파일 갱신
- `list() -> list[Note]`: 전체 목록 반환
- `save()` / `load()`: 명시적 파일 쓰기/읽기, `Note.to_dict()`/`from_dict()`만 사용
- 표준 라이브러리(`json`, `pathlib`)만 사용

**범위 밖(요구사항에 명시 안 됨 — 확인 필요):**
- 동시성/멀티프로세스 접근 제어(파일 락)
- 저장 시 원자적 쓰기(atomic write, 예: temp 파일 후 rename) 여부
- `add()`에서 id 중복 처리 정책(덮어쓸지, 에러 낼지)
- `list()`가 원본 리스트 참조를 주는지 복사본을 주는지(외부에서 변형 시 내부 상태 오염 가능)
- 파일/디렉터리 권한 문제(쓰기 불가 시) 처리 방식
- 인코딩/줄바꿈, 들여쓰기 등 JSON 포맷 세부 규칙

### 리스크 및 애매한 지점
1. **손상된 JSON 파일 처리**: 요구사항은 "조용히 무시/빈 상태 복귀 금지, 명확한 예외"를 명시했지만, 정확히 어떤 예외 타입(예: `json.JSONDecodeError`를 그대로 전파할지, 커스텀 `NoteStoreError`로 감쌀지)과 메시지 포맷을 쓸지는 결정되지 않음 — 설계 시 확정 필요.
2. **`load()`가 언제 호출되는가**: `__init__`에서 파일 있으면 자동 호출은 명시됐으나, `load()`를 외부에서 재호출할 때 메모리 상태를 덮어쓰는지(현재 미저장 변경사항 유실 가능) 여부가 불명확.
3. **`data["tags"]` 등 필수 키 누락 시**: `Note.from_dict`가 `KeyError`를 던질 수 있는데, 이것이 "손상된 파일" 케이스로 함께 취급되는지 별도 처리인지 불명확.
4. **부분 쓰기 실패**: `save()` 도중 프로세스가 죽으면 파일이 반쯤 쓰인 상태가 될 수 있음(원자적 쓰기 미언급) — 다음 `load()`에서 손상 예외로 이어질 위험.
5. **성능**: 매 `add`/`delete`마다 전체 파일을 재작성하는 구조라 노트 수가 많아지면 O(n) 쓰기 비용 반복 — 요구사항상 명시적으로 허용된 설계이므로 문제는 아니지만 향후 확장 시 유의점.
6. **경로 타입 처리**: `path: Path | str`을 받는다고 했는데, 문자열로 들어온 경우 내부적으로 `Path`로 통일해야 이후 `exists()`/`open()` 등이 일관되게 동작.

### 결정 필요 사항 (구현 전 확인 권장)
- 손상 JSON 시 예외 타입/메시지 스펙
- `add()`의 id 중복 정책
- `list()` 반환값의 얕은 복사 여부
- 원자적 쓰기 적용 여부(신뢰성 vs 단순성 트레이드오프)
