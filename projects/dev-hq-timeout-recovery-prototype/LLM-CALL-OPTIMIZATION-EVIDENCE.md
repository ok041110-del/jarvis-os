# Evidence — LLM 호출시간 최적화 Prototype (모델 비교 + 출력 최적화)

PR #77(E2E 최적화, 병렬화 우선 권고)에 이어, 개별 LLM 호출 자체의
소요시간을 줄일 수 있는지 검증했다. Sonnet(현재 Baseline)을 기준으로
"더 빠른 모델" 후보(Haiku)와 Opus를 **동일한 고정 Task/Prompt/Input**
(Nestlé Final Report 생성 — 기존 EVIDENCE에서 이미 병목으로 확인된
호출)로 비교했다. `development-hq/mvp/engine.py`는 여전히 한 줄도
수정하지 않았다 — `model_comparison/run_model.sh`는 동일한 CLI 인자에
`--model`만 추가한 순수 진단 스크립트다.

## MODEL 비교 — 실측 결과

| 모델 | TTFT | 총 호출시간(duration_ms) | Output tokens | Output TPS | 비용 |
|---|---|---|---|---|---|
| **Sonnet(Baseline)** | 7.5초 | **78.8초** | 7,481 | ~104.9 tok/s | $0.290 |
| Haiku(더 빠른 모델 후보) | 6.7초 | **147.9초**(Sonnet 대비 +88%) | 11,056(+48%) | ~78.3 tok/s(더 낮음) | $0.154 |
| Opus | 158.0초(TTFT 자체가 응답시간 전체 — 아래 참조) | **159.4초**(Sonnet 대비 +102%) | 14,323(+91%) | 측정 무의미(아래 참조) | $0.858 |

**TTFT**: Sonnet과 Haiku는 비슷한 수준(6.7~7.5초)이었으나, **Opus는
TTFT가 158.0초로 총 호출시간(159.4초)의 99% 이상을 차지했다** — 이는
가시적 텍스트가 나오기 전 내부 추론(thinking)에 대부분의 시간을 쓴
것으로 추정되며, Opus에서는 TTFT를 "응답 시작까지 대기"가 아니라
사실상 "총 소요시간"과 동일하게 해석해야 한다. **Output TPS**: Opus의
TPS(계산상 ~9,750 tok/s)는 이 TTFT 왜곡 때문에 산출 공식
(output_tokens/(duration−TTFT))이 무의미해진다 — 실제 생성은 훨씬
느린 것으로 추정되나 정확히 분리 측정할 수 없었다(이 자체를 관찰로
기록).

**OUTPUT_TOKENS**: 세 모델 모두 완전히 동일한 프롬프트를 받았음에도
스스로 선택한 응답 길이가 크게 달랐다(7,481 / 11,056 / 14,323) —
모델이 클수록/신중할수록 더 길게 쓰는 경향이 관찰됐다.

**CALL_TIME**: **Sonnet이 세 모델 중 가장 빨랐다.** "더 빠른 모델"
이라는 가정하에 선택한 Haiku가 오히려 88% 더 느렸다 — Haiku 자체의
토큰당 생성 속도가 느려서가 아니라(추정컨대 비슷하거나 약간 느림,
TPS 참조), **같은 프롬프트에 대해 스스로 더 긴 응답을 생성했기
때문**이다. Opus는 두 배 이상 느렸다.

## QUALITY — 구조적 완전성 비교

세 모델 모두 프로그램적으로 확인 가능한 기준(11개 섹션 헤더 전부
포함, Disclaimer 포함)을 통과했다 — 산출물 간 **구조적 결함 차이는
발견되지 않았다.** 다만 응답 길이가 서로 다르므로(19,562자 / 44,231자
/ 41,416자) 서술의 상세도·뉘앙스까지 동일하다고 단정할 근거는 이번
프로그램적 검사 범위 밖이다(정성적 전문 검토는 이번 Prototype에
포함하지 않음, 관찰되지 않은 것으로 기록).

## COST

Sonnet $0.290, Haiku $0.154(가장 저렴, 그러나 가장 느림), Opus
$0.858(가장 비싸고 가장 느림). **속도와 비용이 함께 개선되는 모델은
없었다** — Haiku는 비용만 유리하고 속도는 불리, Opus는 둘 다 불리.

## OUTPUT_OPTIMIZATION — 출력 토큰 수 축소의 효과(Sonnet 고정)

Prompt 자체(Report Writer 역할 지시문)는 임의로 바꾸지 않고, 별도
Prototype 전용 부칙(`concise_task_prompt.txt` = 원본 프롬프트 +
"800~1200단어로 간결하게, 단 모든 섹션·모든 데이터 불일치 플래그는
유지"라는 문장 추가)만으로 같은 Sonnet에서 재실행했다.

| | Sonnet(Baseline) | Sonnet(출력 제약) | 변화 |
|---|---|---|---|
| 총 호출시간 | 78.8초 | **38.1초** | **-51.7%** |
| TTFT | 7.5초 | 3.5초 | -53.4% |
| Output tokens | 7,481 | 3,427 | -54.2% |
| 비용 | $0.290 | $0.231 | -20.6% |
| 실제 단어 수 | (미측정) | ~1,176단어 | 목표 범위(800~1200) 내 |
| 섹션/Disclaimer/데이터 불일치 플래그(CHF/DCF/P/E 언급) | 전부 존재 | **전부 존재** | 유지 확인 |

**출력 토큰 수를 줄이는 것이 이번에 시도한 모든 축(모델 교체 포함)
중 가장 크고 가장 확실한 단일 호출 시간 절감 효과를 냈다** — 모델을
바꾸는 것보다 프롬프트에 길이 제약을 추가하는 것이 더 효과적이었다.
다만 이 변경은 project-local `agents.py`의 `report_writer_final_report`
instruction 문구 자체를 바꾸는 것과 동등한 효과이므로(실제 채택 시),
Dividend Stock Team의 Report Writer 역할이 실제로 산출하는 문서의
분량/상세도 정책을 바꾸는 결정이다 — Architecture 변경은 아니지만
Team의 산출물 정책 변경이므로 사용자 승인 없이 적용하지 않는다.

## PARALLEL_COMBINATION — 병렬화(PR #77)와 결합했을 때

PR #77의 Prototype C 실측(Wave1 47.0초 + Wave2 44.9초 + Wave3 74.5초
+ Wave4/Final Report 111.6초 = 278.0초)에서, **Wave4만 이번에 실측한
"Sonnet 출력 제약" 버전(38.1초)으로 대체한 프로젝션**을 계산했다
(Wave4는 이번 실험과 동일한 Final Report 생성 작업이므로 대체가
타당하다 — Wave1~3은 이번에 재실측하지 않아 원래 값을 그대로 쓴다,
즉 이 부분은 실측이 아니라 근거 있는 프로젝션임을 명시한다):

| 구성 | 총 시간 | 원본 순차 대비 |
|---|---|---|
| 원본(개선 없음, 순차) | 541.5초(동일 호출 순차 합산 기준) | — |
| 병렬화만(PR #77 실측) | 278.0초 | -48.7% |
| **병렬화 + 출력 최적화(Wave4 대체, 프로젝션)** | **204.5초** | **-62.2%(2.65배)** |

Synthesis(Wave3, 74.5초)에도 유사한 출력 제약을 적용하면 추가 절감
여지가 있을 것으로 추정되나, 이번에는 Final Report만 실측했으므로
Synthesis에 대한 수치는 제시하지 않는다(추측이 아니라 미실측으로
정직하게 남긴다).

## DECISION

**모델 교체는 채택하지 않는다** — Haiku/Opus 둘 다 동일 Task에서
Sonnet보다 느렸다(실측: +88%, +102%). "모델 변경이 실제 E2E 시간을
줄이지 못하면 채택하지 않는다"는 지시 기준에 따라 기각한다. Sonnet을
Baseline으로 유지한다.

**출력 토큰 최적화는 가장 유망한 후보다** — 단일 축으로는 최대 절감
(-51.7%)을 냈고, 병렬화와 결합 시 프로젝션상 원본 대비 62.2% 절감
(2.65배)까지 가능하다. 다만 이는 project-local Team 산출물 정책
변경에 해당하므로, **이번 Prototype 결과만으로 실제 채택하지
않는다** — 정성적 품질 검토(뉘앙스/상세도 손실 여부)와 사용자 승인이
먼저 필요하다.

**우선순위 갱신**: 병렬화(정상 실행시간, PR #77에서 실측 확정) ≈
출력 최적화(정상 실행시간, 이번에 실측 확정, 병렬화와 결합 가능) >
Checkpointing(실패 시 피해 최소화, PR #76에서 실측 확정) > Timeout
상향(보조) > 모델 교체(기각) > 캐시(효과 제한적) > 호출 자체 제거
(안전한 후보 없음).

## GOVERNANCE

- `development-hq/` 어떤 파일도 수정하지 않았다. `--model` 플래그를
  쓴 진단 호출도 `engine.py`를 거치지 않는 별도 Bash 스크립트다.
- 모델 교체는 기각됐으므로 Governance 판단이 필요 없다.
- 출력 최적화는 project-local `agents.py`의 instruction 문구를 바꾸는
  것과 동등하다 — `development-hq/`를 건드리지 않으므로 RFC가
  반드시 필요한 Architecture 변경은 아닐 수 있다는 판단이나, Team의
  산출물 정책(보고서 상세도)을 바꾸는 결정이므로 사용자 승인 없이는
  적용하지 않는다.
- Architecture/Contract/Governance 문서는 이번에도 전혀 수정하지
  않았다.

## PHASE9_11

모델 교체는 기각되어 더 이상 검토 대상이 아니다. 출력 최적화는
유망하지만 정성적 검증이 남아 있어, **실제 Phase 9~11 재개나
`agents.py` instruction 실채택은 이번 Evidence만으로 진행하지
않는다** — 사용자가 (a) 출력 최적화를 실제 채택할지, (b) 병렬화와
함께 도입할지, (c) 정성적 품질 검토를 먼저 요구할지를 결정해야 한다.

## 관찰되지 않은 것 (명시적으로 기록)

- Synthesis(Wave3)에 대한 출력 최적화 실측 — 시도하지 않음(Final
  Report만 실측).
- 병렬화+출력 최적화 조합의 실제 재실행(전체 11단계) — 프로젝션만
  제시, 실측하지 않음.
- 정성적 품질 비교(전문가 수준의 서술 깊이/뉘앙스 평가) — 프로그램적
  구조 검사(섹션/Disclaimer/키워드 존재 여부)로 대체, 심층 비교는
  범위 밖으로 명시.
- Opus의 실제 순수 생성 속도(TTFT 왜곡 없이) — 측정 방법의 한계로
  분리하지 못함.
- 반복 시행을 통한 통계적 신뢰도(각 조합 1회씩만 실측) — 최소
  Prototype 원칙에 따름, 결과가 방향성 있게 뚜렷해(Haiku/Opus 모두
  명확히 더 느림) 반복의 한계효용이 낮다고 판단.

# Architecture/Contract 변경 여부

**없음.** `development-hq/` 어떤 파일도 수정하지 않았다. 모델 비교는
기각되어 아무것도 채택하지 않았다. 출력 최적화는 유망 후보로
기록했을 뿐 `agents.py`를 실제로 수정하지 않았다. 새 Capability, 새
Agent, 새 Kernel Component, 새 Contract를 만들지 않았다. v1.0
Freeze를 해제하지 않았다. RFC/ADC/ADR 문서를 작성하지 않았다. 구현
채택도, Phase 9~11 재개도 하지 않았다 — 전부 사용자 승인 이후로
남긴다.
